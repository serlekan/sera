### 2.6 Existing locking and concurrency

**None.** `new_task` relies on `task_dir.mkdir(exist_ok=False)` as its only
concurrency guard. Every ledger append is a bare `open("a")`. Spec Section 5
mandates a cross-platform atomic lock directory under the task runtime directory
and an equivalent repository-registry lock. This is new infrastructure (I1-T03).

### 2.7 Existing packet / review / verification / seal logic

- Packet: `generate_packet` (Markdown), `write_packet_provenance` /
  `read_packet_provenance` (v3 JSON sidecar), `packet_state` (ordered
  fail-closed currency: missing → unbound → contract → head → tree → state →
  coverage → change set → route → content).
- Review: `record_review` / `accept_review` (re-validates packet currency, then
  reads HEAD from git — never trusts a supplied SHA), `evaluate_review_record`,
  `read_reviews`, `review_ledger_fingerprint`. Verdicts `ship` / `fix-first` /
  `rethink`; stages `independent` / `gate` / `supplementary`.
- Verification: `run_verification` (`subprocess.run(shell=True)` over
  `task["verification"]`, stops on first non-zero), `record_evidence`,
  `read_ledger`.
- Seal: `create_seal` (calls `check_task`, requires `ok`), `evaluate_seal`
  (schema-first), single `seal.json`. `SEAL_V2_REQUIRED_FIELDS`,
  `SEAL_V2_ONLY_FIELDS`.

### 2.8 Existing provider / model routing

`RouteDecision` dataclass; `decide_route(root, task, repo_map)` picks
`builder` / `reviewer` / `gate` lanes from `config["lanes"]` plus budgets;
`lane_label`, `resolved_route_identity`. No provider is ever invoked
(`generate_packet` and `next_action` explicitly hand off). SERA 0.5.0 keeps
this: native dispatch stays deferred (Section 19).

Per-file local helpers (no shared `conftest`): each test module defines its own

## 4. Increment scope and ordering

### 4.1 The three increments

```text
Increment 1 — Provenance Foundation   (this plan, task-level detail)
Increment 2 — Evidence Integrity      (Section 16, dependency-proof detail)
Increment 3 — Controller UX and Release (Section 17, dependency-proof detail)
```

Dependency (spec Section 1): `provenance foundation → evidence integrity →
reporting and release`. Each increment leaves the repo green and testable; each
increment's independent review binds its exact reviewed state and becomes
historical when a later commit lands. No increment review substitutes for the
fresh final release review and gate.

### 4.2 Increment 1 — in scope

Everything in spec Section 24.1, i.e. the complete provenance foundation its own
exit review consumes: `schemas.py`; canonical serialization + ledger
fingerprints; Config v2 compatibility; `PolicySnapshotV1`; `RouteSnapshotV1`;
`TaskContractV2` + `TaskContractAdoptionV1` + `task-contracts.jsonl` authority;
`RepositoryIdentityV1`; canonical roles + implementation origin;
`SubstitutionDecisionV1` + single-use manual authorization;
`ExecutionEvidenceSourceV1` + repository source registry;
`ExecutionRepositoryStateV1`; `PacketModelV1` + Packet v4 Core Binding;
`ExecutionTargetV1`; `ExecutionBindingV1` + registered verifier boundary;
`ExecutionStateEvidenceV1` + effective-class derivation; SERA Registered External
Runner V1; `ExecutionReceiptV1` + `ReceiptImportRecordV1`; Review v2;
`AssuranceState` foundation + reason codes + sequencing; builder input A → output
B semantics with strict input enforcement; non-mutating validator/reviewer/gate
semantics; execution-window evidence; Seal v3 + `seals.jsonl` authority +
optional derived `seal.json` pointer; the receipt-import / source-registration /
generic-execution-runner / task-contract-adoption / policy-adoption /

### 4.3 Increment 1 — explicitly NOT in scope

Verification v2; Packet v4 `evidence_integrity` sections; packet lint;
deterministic context reduction; overflow manifests; knowledge-fingerprint

release workflow. (Spec Sections 24.1, 16, 15, 17, 3.2.)

### 4.4 Increment 1 dependency-correct coding order

Validated against the repository. The spec's suggested order holds, with these
repository-driven refinements:

1. **Ledger + lock infrastructure precedes every schema** — there is no locking
   today (Section 2.6) and `read_ledger`/`read_reviews` are non-strict; the
   strict `LedgerReader` and the lock primitive are prerequisites for *any*
   authoritative append, so they lead (I1-T02, I1-T03).
2. **`RepositoryIdentityV1` before Config v2** — config v2's
   `repository identity requirement` and the policy snapshot both embed it.
3. **`ExecutionRepositoryStateV1` before `TaskContractV2`** — the contract's
   modern `task_fingerprint` derivation and the adoption record both embed
   repository state, and the state object reuses the existing review-change
   algorithm which is stable today.
4. **Policy + route snapshots before substitution** — `SubstitutionDecisionV1`
   binds `policy_hash` and `route_hash`.
5. **Source registry before target/binding/evidence** — the target records
   `creation_source_registration_hash`; the binding and evidence records resolve
   the registration.
6. **Packet v4 Core Binding before target creation** — target creation is
   deliberately post-packet and non-circular (spec 16.1): packet hash P must be
   final before `ExecutionTargetV1` is created.
7. **Runner + binding before execution-state evidence** — the effective class is
   derived from a `VERIFIED` binding.
8. **Receipt import + validation before Review v2** — Review v2 is
   receipt-backed.
9. **`AssuranceState` after all evidence domains, before Seal v3 and CLI
   wiring** — the seal and every CLI verb delegate to it.
10. **Self-hosting bootstrap last**, then the Increment 1 independent review.

Resulting order:

```text
characterization tests
  -> schemas + canonical serialization + reason-code registry skeleton
  -> strict LedgerReader + append-only ledger primitive + ledger fingerprint
  -> task mutation lock + repository registry lock + lock ordering
  -> RepositoryIdentityV1
  -> Config v2 compatibility translator
  -> ExecutionRepositoryStateV1
  -> PolicySnapshotV1 + policy-snapshots.jsonl + `sera task policy --adopt`
  -> RouteSnapshotV1 + route-snapshots.jsonl
  -> canonical roles + implementation origin
  -> TaskContractV2 + TaskContractAdoptionV1 + task-contracts.jsonl authority
       + modern task_fingerprint change
  -> `sera task contract --adopt` trusted operation
  -> SubstitutionDecisionV1 + substitution-decisions.jsonl
       + `sera substitution authorize` + classification derivation
  -> ExecutionEvidenceSourceV1 + repo registry + `sera evidence-source register`
       + built-in checkpoint registration + verifier resolution table
  -> PacketModelV1 + Packet v4 Core Binding + packet-<stage>.json
  -> ExecutionTargetV1 + execution-targets.jsonl + target backends
  -> Registered External Runner V1 + ExecutionBindingV1 + `sera execution run`
  -> ExecutionStateEvidenceV1 + effective-class derivation
  -> ExecutionReceiptV1 + ReceiptImportRecordV1 + `sera receipt import`
  -> receipt validation ordering + replay/conflict + builder A->B / non-mutating
  -> Review v2 + `sera review --receipt`
  -> independence + sequencing rules
  -> AssuranceState + reason-code registry finalization
  -> Seal v3 + seals.jsonl + derived pointer + `sera check --require-seal`
```

### I1-T02 — `schemas.py`: strict readers, canonical JSON, hashing, import-lint

- **Purpose:** the shared serialization + hashing + strict-parse primitive every
  new record depends on (spec Section 5).
- **Specification obligations:** Section 5 (canonical JSON: sorted keys, no
  insignificant whitespace, Unicode preserved, finite values only, array order
  preserved); Section 10.6 / 10.6a (byte caps, object root, unknown-field
  rejection, string/hash/timestamp/number bounds, depth/key caps); Section 18.3
  (hash confusion — named domains, lowercase hex).
- **Existing code inspected:** `sha256_text`, `sha256_bytes`,
  `json.dumps(sort_keys=True, separators=(",",":"), ensure_ascii=False)` idiom
  used by `task_contract_fingerprint` / `route_fingerprint` (reuse the exact
  serialization; add the domain-separator hashing on top).
- **Files expected to change:** none.
- **Files expected to add:** `src/sera/schemas.py`,
  `tests/test_schemas.py`, `tests/test_module_boundaries.py`.
- **Symbols / APIs affected (new):** `canonical_json(obj) -> str`;
  `sha256_domain(domain: str, *parts: bytes) -> str`;
  `read_strict_json(raw: bytes, *, max_bytes, max_depth, max_keys, spec) ->
  dict` (spec = a bounded field descriptor); `require_hash`, `require_timestamp`,
  `require_bounded_str`; `SCHEMA_VERSIONS: dict[str,int]`.
- **Persisted artifacts affected:** none yet.
- **Dependencies:** prerequisite: T01. Enables: T03 and every schema task.
- **Detailed implementation steps:**
  1. `canonical_json`: reject non-finite floats (`math.isfinite`), `bool` where

## 9. Schema implementation plan

Common rules for every Increment 1 schema (spec Section 5):

- **Python representation:** a builder function returning a plain `dict`; a
  `validate_*` function; no dataclass on the wire (JSON dicts), frozen
  dataclasses only for in-memory views (`ConfigV2View`, `AssuranceState`).
- **Validation boundary:** `schemas.read_strict_json` with a per-schema field
  descriptor at every ingest; internal construction goes through the builder.
- **Canonical serialization:** `schemas.canonical_json` (sorted keys, `(",",":")`,
  `ensure_ascii=False`, finite only).
- **Stable hash:** `schemas.record_hash(domain, obj, exclude={"<self>"})` —
  `<self>` is the record's own hash field and **nothing else** (spec repeats
  "No other field is excluded" for every schema).
- **Reader version handling:** integer `schema_version`; strict readers reject
  missing / Boolean / non-integer / negative / unsupported.
- **Writer version:** the current integer for that artifact.
- **Unknown field policy:** rejected on read.
- **Bounds:** Section 10.6 / 10.6a limits for receipt + external evidence
  payloads; other records use the same string/hash/timestamp helpers.
- **Duplicate handling:** exact canonical repeat retained + deterministic
  diagnostic (`exact_duplicate_registration`, `*_DUPLICATE`).
- **Conflict handling:** same id + different canonical content → `*_CONFLICT`,
  fail closed.
- **Legacy handling:** a compatibility normalizer per family; legacy records
  labeled, never rewritten.
- **Test location:** `tests/test_schemas.py` for primitives; one
  `tests/test_provenance_<domain>.py` per schema.

## 10. Ledger implementation plan

**Decision:** introduce **one** append-only ledger primitive (`schemas.LedgerReader`
+ `append_ledger_record`, I1-T03) rather than a generic event store or a
per-schema bespoke store. It is narrow: strict per-line parse, order-sensitive
fingerprint, single-write append, malformed-blocks. The existing non-strict
`read_ledger` / `read_reviews` stay until their owning task rewires them (T13
does not rewire `read_ledger`; the legacy verification ledger keeps its reader
in Increment 1 and gets Verification v2 in Increment 2 — Section 16).

## 11. Locking and concurrency plan

Current state: **no locking** (Section 2.6). New (I1-T04):

- **Task mutation lock:** `os.mkdir(<task_dir>/.lock)`; fail-closed acquire with
  bounded retry; **no silent stale removal** — a leftover lock dir surfaces an
  operator error. Every task-scoped mutating op (policy adopt, contract adopt,
  substitution authorize, target create, binding append, receipt import, review
  record, seal) holds it; the record is serialized + written as one UTF-8 append
  while held.
- **Repository registry lock:** `os.mkdir(.sera/.registry.lock)` for
  `.sera/execution-evidence-sources.jsonl` append.
- **Lock ordering (enforced by `with_registration_then_task` and a probe test):**
  a task operation **resolves and validates an already-persisted registration
  under the registry lock, releases it, then takes the task lock, then re-reads
  that exact registration hash under the task lock** before appending task
  evidence. It never creates or changes a source registration as a side effect
  of receipt/evidence import.
- **Forbidden:** `task_lock` held while acquiring `registry_lock`. The two locks
  are never held simultaneously — this structurally prevents inversion, so
  ordering is "registry first, fully released, then task", not "nested".
- **Atomic append strategy:** one `write()` of the full canonical line + `\n`;
  `flush` + best-effort `os.fsync`; no partial-line tolerance on read.
- **Pointer replacement (`seal.json`):** write to a temp file in the same
  directory, `os.replace` (atomic on Windows + POSIX). Only after the
  authoritative `seals.jsonl` append succeeds.
- **Cleanup behavior:** worktree/sandbox cleanup (`git worktree remove`, `rmtree`)
  never touches any `.jsonl`.
- **Stale lock behavior:** reported with pid/host/age from the lock metadata
  file; operator removes it manually. No timeout auto-break (no `signal` on
  Windows anyway).

## 13. Task v1 → Task v2 planning

Preserves: legacy `task.json` (untouched, in place), the historical legacy
`task_contract_fingerprint` (`previous_task_contract_fingerprint`), all legacy
evidence (stays legacy). Creates: `task-contracts.jsonl` with one
`TaskContractAdoptionV1` embedding the complete `TaskContractV2`.

`sera task contract --adopt` flow (T12, verbatim Section 7.5):

1. capture — read legacy/active contract + compute its contract hash;
2. capture — repository identity, HEAD, tree;
3. resolve and, if required, append the immutable policy snapshot;
4. require explicit origin, actor, reason, policy result, structured
   `bootstrap_limitations`;
5. construct the complete new `TaskContractV2` + `TaskContractAdoptionV1`;
6. re-read active contract, repository identity, HEAD/tree, policy;
7. fail without appending if any captured value changed
   (`TASK_CONTRACT_ADOPTION_STALE` / `_REPOSITORY_MISMATCH`);
8. append exactly one adoption record (embedding the new contract);
9. only after authoritative append, optionally write a non-authoritative v2
   `task.json` projection **when no historical v1 file occupies that path**.

- **Bootstrap limitations:** actor, reason, exact Increment 1 scope, legacy
  verification evidence allowed, modern stages still required, policy result,
  adopted contract, assurance limitations.
- **Re-read + append + optional projection:** projection failure after a
  successful ledger append cannot roll back the adoption; the command reports a
  recoverable projection error.
- **Duplicate/conflict:** exact duplicate → `TASK_CONTRACT_ADOPTION_DUPLICATE`
  (observable, blocks strict until explained via immutable policy); same
  `adoption_id` + different content → `TASK_CONTRACT_ADOPTION_CONFLICT` (fail
  closed).
- **Failure behavior:** no partially modern task; malformed/truncated first line
  is invalid under Section 5.

## 15. Registered runner model (the builder input/output detail)

This is the highest-ambiguity area. The plan resolves it explicitly.

### 15.1 Non-mutating stages (validator, reviewer, gate)

```text
immutable exact-state target T(A)   [immutable_git_target | runner_sandbox | content_addressed_snapshot]
  -> runner executes the external command against T(A) with cwd = T(A) path, shell=False
  -> T(A) is unchanged (read-only where the OS permits; identity revalidated after)
  -> receipt.output_state MUST be absent
  -> observed post-stage governed state MUST equal input_state
     else NON_MUTATING_STAGE_REPOSITORY_CHANGED (receipt unusable even if verdict = success)
```

Equal controller checkpoints alone = `CHECKPOINT_OBSERVED` only. Strict
exact-state eligibility for these stages requires a policy-accepted registered
source + `VERIFIED` `ExecutionBindingV1` to the exact T(A) (Section 10.2.5).

### 15.2 Builder stage (mutating; A → B)

```text
immutable governed input identity A               (Packet v4 Core Binding input_state)
  -> ExecutionTarget T(A/P): read-only immutable_git_target OR runner_sandbox from A
  -> registered enforcement source R launches the builder command with cwd inside a
     CONTROLLED WRITABLE EXECUTION WORKSPACE derived from A
       * git worktree:  `git worktree add <workspace> A` (detached), writable, under the
         excluded task runtime dir; branch/ref strategy = detached HEAD at A, no named branch
       * the workspace is NOT required to remain immutable — the builder writes here
  -> builder produces a COMMITTED output in the workspace (commit B', tree, task-change identity)
  -> OUTPUT EXTRACTION: SERA reads B' commit/tree/change-fingerprint from the workspace
  -> OUTPUT INTEGRATION: the exact commit is integrated into the governed repository
     (fast-forward / apply the identical commit object) producing governed HEAD B
  -> OUTPUT OBSERVATION: SERA independently observes governed state B and compares
     commit id, tree, and complete task-change fingerprint to the builder's claim
  -> input identity A remains independently provable: T(A) identity + the VERIFIED
     E->T(A) binding are unchanged by anything the builder did in its workspace
  -> receipt.input_state = A ; receipt.output_state = committed B ; both bind the
     active contract + dynamic task fingerprints
  -> builder currency: current implementation state MUST equal B (compare to B, never A)
```

- **Immutable base/input target:** `immutable_git_target` T(A/P) — never written
  by the builder. Its `VERIFIED` binding is the strong evidence for **input A**
  (Section 9: "the evidence proves that the builder consumed governed input A; it
  does not prove output B").
- **Writable builder worktree/overlay:** a separate `git worktree add --detach`
  under `<task_dir>/execution-workspace/<execution-id>/`. Path identity is
  irrelevant; Git + task identity are authoritative (Section 10.1).
- **Output commit extraction:** `git -C <workspace> rev-parse HEAD` + tree +
  `review_change_fingerprint` over the workspace delta.
- **Target revalidation:** after the builder completes, re-validate T(A/P)
  identity (unchanged) before recording the binding.
- **Output integration:** the identical commit object is placed on the governed
  branch (same SHA). A **cherry-pick that creates a different commit is a
  different output state** (Section 10.1). A **patch-only handoff is
  external/manual** until integrated, validated, and observed.
- **Output observation:** governed HEAD/tree/change-fingerprint compared to the
  claim; mismatch → `EXECUTION_OUTPUT_STATE_MISMATCH`.
- **Cleanup:** `git worktree remove` the workspace and T(A/P); ledgers untouched.
- **Uncommitted output:** only under an explicit non-strict policy
  (`BUILDER_OUTPUT_UNCOMMITTED_NOT_ALLOWED` under strict); binds the complete
  current review change fingerprint; reported as limited provenance.
- **Out-of-scope / omitted output:** the review change fingerprint covers the
  **complete** task delta (reusing the existing coverage guarantee); an
  output-state binding cannot hide out-of-scope or omitted task changes.
- **Excluded-ledger appends:** do not stale the builder receipt (dynamic
  fingerprint excludes them — T13).

### 15.3 Git worktree specifics

- **Creation:** `git worktree add --detach <path> <rev>` where `<path>` is under
  `<task_dir>/execution-{target,workspace}/…` (an `is_sera_runtime_path` /
  excluded location).
- **Path containment:** validated `resolve()`d-under-task-dir before use;
  symlink escape rejected.
- **Branch/ref strategy:** detached HEAD only; no named branch is created; the
  output commit's identity is a raw object id.
- **Detached HEAD behavior:** expected and required; the builder commits on a
  detached HEAD; SERA extracts the commit id.
- **Cleanup:** `git worktree remove --force` + prune; on failure the stale
  worktree is reported, never silently deleted from the ledger.
- **Commit identity:** the integrated governed commit MUST equal the workspace
  commit object id.
- **Integration into the governed repository:** `git merge --ff-only` of the
  detached commit, or direct ref update to the identical object; any operation
  that rewrites the commit id invalidates strict builder provenance.

No implementation ambiguity remains for T17 / T18 / T21.

## 16. Generic runner security (I1-T18, T20)

- **argv, no shell:** `subprocess.run([*argv], shell=False, cwd=<T path>,
  env=<controlled allowlist>)`. `core.run_verification`'s `shell=True` is **not**
  reused for the runner.
- **Controlled cwd:** the target/workspace path only.
- **Bounded environment:** an explicit allowlist —
  `SERA_EXECUTION_ID`, `SERA_TARGET_PATH`, `SERA_PACKET_PATH`,
  `SERA_OUTPUT_PATH`, `SERA_RECEIPT_PATH`, `PATH`, minimal locale
  (`LANG`/`LC_ALL`). SERA controls all `SERA_*` values. Nothing from repository
  content, receipt JSON, or task text becomes an argument or an env value.
- **Registered command template:** the argv form is fixed by the source
  registration's `command-template fingerprint`; `sera execution run -- <argv>`
  must match the registered template shape.
- **How external commands receive paths:** via the `SERA_*` env vars and/or
  fixed argv positions in the registered template — never by interpolating
  repository text.
- **Receipt import:** performs no shell interpolation, invokes no provider,
  derives no path from receipt-controlled values, treats `execution_id` as data.

## 17. `ExecutionBindingV1` verification plan (I1-T18)

- **Who constructs it:** the trusted internal domain boundary in `provenance.py`,

- **Untrusted input:** the external evidence payload (bounded-parsed;

## 30. Self-hosting Increment 1 bootstrap sequence

Executed only after all Increment 1 code exists (I1-T27); scripted in
`test_end_to_end_increment_1.py` on a synthetic repo first.

1. baseline tests (`python -m unittest discover -s tests` green; 297 + new).
2. `sera evidence-source register` — create/resolve the exact SERA Registered
   External Runner V1 source R (ceiling `EXECUTION_STATE_ENFORCED`).
3. candidate policy creation — `sera task policy --adopt` with a v2 candidate
   snapshot accepting R's `registration_hash` with enforced capability for the
   self-hosting review target/stage.
4. Task v1 → Task v2 explicit adoption — `sera task contract --adopt --origin
   pre_existing --actor <actor> --reason <reason>` with empty/unassessed
   knowledge and structured bootstrap limitations; original Task v1 unchanged.
5. Packet v4 Core Binding generation — `sera packet review` regenerates a
   `feature_level: core_binding` packet for the exact current Increment 1 state
   and active Task v2 fingerprint.
6. legacy verification — `sera verify` runs and is recorded as
   `LEGACY_PROVENANCE` / bootstrap-permitted only because the immutable policy
   allows that exact Increment 1 verification scope.
7. exact immutable review target — `sera execution run --stage
   independent_reviewer --source-registration <hash>` creates execution E and
   target T(A/P); R launches/directs the provider-neutral external reviewer
   against T.
8. verified `ExecutionBindingV1` — R's registered verifier returns `VERIFIED`;
   effective `EXECUTION_STATE_ENFORCED` evidence becomes eligible.
9. receipt import — `sera receipt import <receipt.json> --output-file <output>`;
   the reviewer output references E/P/T/binding/evidence.
10. receipt-backed independent review — `sera review --receipt <execution-id>`;
    validation rechecks R, policy, binding, and all execution context.
11. required gate — if the policy requires it, an equivalent registered-source /
    binding chain for `release_gate`.
12. AssuranceState check — `sera check` / `sera next`.
13. optional mixed-provenance Increment 1 Seal v3 — `sera seal` records legacy
    verification + modern review + `overall_provenance: mixed`; checkpoint only,
    not release-grade.
14. independent review of the exact Increment 1 HEAD — fresh context, exact
    state.

Bootstrap evidence is distinguished from final release-grade evidence in the
tracked log (`docs/superpowers/plans/…-increment-1-bootstrap-log.md`, committed
in Increment 3).

## R1 §A — PLAN-001: builder execution binds the actual writable workspace

### A.1 Problem restated

The parent plan (§15.2) already separated an immutable `T(A/P)` from a writable
builder worktree, but the **binding** was described as `E → T(A/P)`. A `VERIFIED`
`E → T(A/P)` does not by itself prove that execution `E` operated in the writable
workspace `W`, nor that `W` was derived exactly from governed input `A`.

### A.2 Three distinct identities (never collapsed)

```text
T = immutable base / input-evidence target
    ExecutionTargetV1, target_kind = immutable_git_target | content_addressed_snapshot,
    repository_state = A, immutability_class = structurally_enforced
W = writable builder execution workspace
    derived from T; NOT an ExecutionTargetV1 record; identity captured in the
    binding's evidence artifact (A.4)
B = produced committed implementation output
    established independently under spec §10.1 (extraction → integration → observation)
```

### A.3 Required builder execution chain

```text
Packet P(A)                                     [Packet v4 Core Binding, input_state = A]
  → immutable governed base target T(A/P)        [ExecutionTargetV1 appended, boundary 5]
  → controlled writable workspace W derived exactly from T/A
  → pre-launch validation:
        W.head_sha == A.head_sha
        W.tree_sha == A.tree_sha                 [git content address of A]
        `git -C W status --porcelain` empty      [no pre-launch delta]
        W derivation parent == T.target_hash
        W contract/task identity == expected
     failure → workspace_base_validation = FAILED|INDETERMINATE, binding not VERIFIED
  → execution E launched by the registered runner with W as its actual cwd/workspace
        subprocess([*argv], cwd=W_realpath, env=<allowlist>, shell=False)
        record: resolved cwd realpath, pid, argv-template fingerprint, started_at
  → machine-verified relation, all in one canonical evidence artifact (A.4):
        E → W            (launch-to-workspace association)
        W ← derived-from ← T(A/P)   (W_pre == A; parent == T.target_hash)
  → builder mutates W                            [expected; W is writable by design]
  → committed output B' in W                     [strict: HEAD advances, no residual delta]
  → output extraction: B' commit SHA, tree SHA, complete task-change fingerprint,
        active contract fingerprint, dynamic task fingerprint
  → exact-object integration into the governed repository (A.6) → governed state B
  → independent observation: governed B == claimed B  (spec §10.1, §11 step for builder)
  → T(A/P) revalidated UNCHANGED after execution   [it is immutable input evidence]
```

`ExecutionBindingV1` for the builder:

```text
target_id / target_hash   = T(A/P)                         [matches spec §19 "E -> T(A)"]
expected_state            = A
binding_method            = immutable_target_process_binding
evidence_artifact_hash    = SHA-256 of BuilderWorkspaceBindingEvidenceV1 (A.4)
binding_result            = VERIFIED  iff  all of:
                              T materialized and verified == A
                              W derived from T, W_pre == A, W_pre clean
                              E launched with cwd == W_realpath
                              argv matched the registered command template
                              T revalidated unchanged post-execution
                            else FAILED (a check failed) or INDETERMINATE
                              (the backend could only prove working-directory intent — spec §10.2.4)
```

For **non-mutating** stages (validator / reviewer / gate): `W == T`, a read-only
`immutable_git_target`; `binding.target_id = T`; post-execution `T` must be
unchanged; no writable workspace, no `BuilderWorkspaceBindingEvidenceV1`
workspace fields beyond `workspace_kind = read_only_target`.

### A.4 `BuilderWorkspaceBindingEvidenceV1` — implementation artifact (schema-compatible)

**It is not a normative persisted schema.** It is the bounded canonical content
addressed by `ExecutionBindingV1.evidence_artifact_hash` (spec §10.2.3: that
field is "optional" and the `BindingVerificationResult` explicitly carries an
"optional evidence artifact hash"; spec §10.6a: "only content hashes, byte
counts, canonical binding results, and bounded verifier diagnostics cross the
trusted boundary"). Its content is stored **content-addressed in excluded task
runtime storage** — `<task_dir>/execution-binding-evidence/<sha256>` — exactly
like verified raw output (spec §10.7). Only its hash enters
`execution-bindings.jsonl`.

```text
schema_version: 1
execution_id
base_target_id
base_target_hash
workspace_kind: detached_git_worktree | isolated_copy | read_only_target | other_registered_backend
workspace_path_identity            # resolved realpath, DIAGNOSTIC ONLY, never a trust identity
workspace_pre_head_sha
workspace_pre_tree_sha
workspace_parent_target_hash        # == base_target_hash; proves W ← T
packet_hash
repository_identity
task_contract_fingerprint
task_fingerprint
policy_hash
route_hash
launch_cwd_identity                 # resolved realpath of the process cwd == workspace_path_identity
process_identity                    # pid + start time, LOCAL DIAGNOSTIC ONLY
workspace_base_validation: VERIFIED | FAILED | INDETERMINATE
launch_binding_result: VERIFIED | FAILED | INDETERMINATE
recorded_at
artifact_hash                       # SHA-256 over the canonical record excluding artifact_hash
```

Authoritative identities remain Git/content hashes (`*_tree_sha`,
`base_target_hash`) and the registered-runner observation. Raw path strings are
diagnostics only.

### A.5 Builder workspace creation — exact pre-launch workflow (updates §15.3)

```text
1. Packet v4 finalizes P(A).
2. Immutable base target T(A/P) is materialized (git worktree --detach at A,
   or `git archive` of A's tree into a read-only dir) and verified == A.
   ExecutionTargetV1 appended (boundary 5).
3. T identity verified: `git -C T rev-parse HEAD^{commit}` == A.head_sha,
   `HEAD^{tree}` == A.tree_sha, `status --porcelain` empty.
4. Builder workspace W created from exact A/T:
   `git worktree add --detach <W> A`  (a SEPARATE worktree from T), OR
   copy T's archived tree into a fresh writable dir.
5. W independently observed before execution.
6. Require: W.head == A.head ∧ W.tree == A.tree ∧ W clean ∧
   W parent == T.target_hash ∧ W contract/task identity == expected.
7. Only then authorize E.
8. Runner launches the builder with actual cwd/workspace = W.
9. Runner records the launch-to-W relationship (A.4).
10. T remains immutable and is revalidated after execution.
If W does not exactly derive from A → workspace_base_validation = FAILED |
INDETERMINATE → no strong builder input evidence.
```

### A.6 Builder integration ordering (updates §15.2 "output integration")

```text
workspace B'
  → verify exact object identity (commit SHA, tree SHA, task-change fingerprint)
  → governed repository still at expected predecessor A?
        NO  → do NOT rewrite / cherry-pick / manufacture a new B; fail closed;
              require a new execution (EXECUTION_OUTPUT_STATE_MISMATCH / BUILDER_OUTPUT_STALE)
        YES → integrate the identical commit object B' (git merge --ff-only, or a
              ref update preserving the exact SHA)
  → observe governed B; require governed B == claimed B == B'
```

A cherry-pick that produces a different SHA is a **different output state**
(spec §10.1). A patch-only handoff is external/manual until integrated,
validated, and observed.

### A.7 Builder execution-binding **semantics** (spec-limited)

"Effective input-enforcement" for the builder means: *SERA established through
the registered enforcement boundary that the builder process executed in a
controlled workspace whose pre-execution implementation state exactly derived
from the governed immutable input target `T(A/P)`.* It does **not** mean the
builder was prevented from modifying `W` (modification is the point). It does
**not** prove provider identity, authorship, absence of external filesystem
access, or a non-collusive local administrator (spec §10.2.4). Those limitations
are recorded in `ExecutionStateEvidenceV1.limitations` and reported.

### A.8 Post-execution validation — two different checks

```text
Base target T:   MUST remain unchanged   (re-verify head/tree/porcelain == A)
Workspace W:     MUST begin at A, MAY end at B'   (no "unchanged" check against W)
```

The generic "target must remain unchanged" check applies to `T` (and to `W` only
for non-mutating stages where `W == T`), never to a builder's writable `W`.

### A.9 Builder output extraction — strict acceptance conditions (updates §15.2, §20)

```text
workspace pre-state  = A
workspace post-state = B'
strict builder output counts only if:
  B' is committed (HEAD advanced past A)
  exactly one accountable output commit (or an explicitly bounded set)
  no residual staged/unstaged/relevant-untracked builder delta outside B'
  no out-of-scope relevant mutation
  no unexpected baseline mutation
  contract identity in B' == active contract
otherwise blocked, unless the spec's already-defined non-strict working_tree
path is explicitly permitted by policy (spec §10.1 case B).
```

### B.4 Self-hosting platform

Actual environment (from repository reality and the working environment):
**Windows 11** is the primary self-hosting development platform; the package is
cross-platform (stdlib only, `requires-python >=3.11`, `git` CLI).

The chosen backend's VERIFIED basis — *separate tree materialized from A's exact
content address + controlled launch handles + pre/post identity verification +
machine-observed launch association* — is **platform-neutral**. It relies on
`git worktree` / `git archive` (both Windows + POSIX), `subprocess` with `cwd`
(both), and `os.path.realpath` (both). **No POSIX-only path; no Windows-only
path.** Filesystem read-only attributes (`attrib +R`, `os.chmod`) are used only
as defence-in-depth and are explicitly **not** the basis of any VERIFIED claim
(spec §10.2.4; remediation §19: "Windows read-only file attribute != security
sandbox; POSIX chmod != complete process sandbox; cwd != filesystem
confinement").

```text
Windows backend: git worktree --detach / git archive + subprocess(cwd, env allowlist, shell=False)
POSIX backend:   identical
```

Policy may grant strong assurance only on a backend whose enforcement capability
has actually been established by I1-T04A.

### B.5 What `EXECUTION_STATE_ENFORCED` means for Registered External Runner V1

Minimum mechanically verifiable property (non-mutating stage):

```text
E was launched by the registered runner
cwd (resolved realpath) == a target directory SERA materialized from exactly A/P
that directory's git tree identity == A.tree_sha BEFORE launch
that directory's git tree identity == A.tree_sha AFTER execution (non-mutating)
the runner passed only controlled target handles (SERA_TARGET_PATH == that dir;
  the governed checkout path was never passed)
the runner recorded the process→directory association (pid, realpath, argv template)
argv matched the registered command-template fingerprint
```

For the builder, replace the "AFTER == A" check with "T(A/P) unchanged AFTER" +
"W_pre == A recorded" + "W parent == T.target_hash".

Whether this is sufficient to say "structurally constrained to consume `T`" under
the locked spec: **YES**, at the spec's own documented strength. Spec §10.2.4
states the runner "establishes only that the registered boundary
launched/directed E against T to its documented local enforcement strength" and
that it "does not prove … that the process read no external non-repository data
… Those limitations are reported." A separate content-addressed tree +
controlled handles + verified identity is materially more than "working-directory
intent" (which the spec calls INDETERMINATE). The residual — a determined child
could open the governed checkout by absolute path — is a **disclosed limitation
in `ExecutionStateEvidenceV1.limitations`**, exactly as the spec requires, not a
downgrade.

If, on the actual platform, the backend cannot give a stable resolved-realpath
association or cannot verify the materialized tree identity, the result is
`INDETERMINATE` and the P0 gate fails (B.7).

```text
- the child process may perform network I/O
- a local actor controlling both the runner and the repository is not excluded
```

## R1 §C — PLAN-003: `AssuranceState` consistent-read model

### C.1 Problem restated

The parent plan (I1-T24) said `derive` "reads a consistent snapshot under a
shared read", but no shared-read lock exists and the model was undefined.

### C.2 Chosen model — **exclusive task-lock derivation**

```text
AssuranceState.derive(root, task_dir):
    with task_lock(task_dir):          # the SAME exclusive lock used for task mutation
        return _derive_locked(root, task_dir)

AssuranceState._derive_locked(root, task_dir):
    # PRECONDITION: caller already holds task_lock(task_dir)
    assert task_lock_held(task_dir)    # ownership probe; raises if not held
    ...derive every field from the domain modules...
```

- `sera check`, `sera next`, `sera status`, `sera check --require-seal` call the
  public `derive()` (it owns its consistency boundary).
- `sera seal` and any trusted mutating operation that needs assurance **while
  already holding `task_lock`** calls `_derive_locked()` directly — because
  `task_lock` is intentionally **non-reentrant** (I1-T04). No recursive
  acquisition.
- Readiness derivation is a **read that takes the exclusive lock**. This is
  correct for consistency; a long mutating operation briefly blocks a concurrent
  `status`. Acceptable for a local CLI; documented in `sera status --help` and
  the release notes.

### C.3 Model comparison (decision locked, not left to implementation)

| Criterion | Exclusive task-lock derivation (CHOSEN) | Optimistic capture / re-read |
| --- | --- | --- |
| Complexity | low — one lock, no retry loop | higher — capture set, re-read, bounded retry, `STATE_CHANGED_DURING_DERIVATION` path |
| Cross-platform correctness | same primitive as mutation (`os.mkdir` lock), already proven in I1-T04 | correct but more moving parts |
| Deadlock risk | none — single lock, non-reentrant, `_derive_locked` for the held-lock case | none, but lock-ordering with registry must still be respected |
| Latency | a `status` call may wait for an in-flight mutation (seconds at most; ledgers are small) | never blocks, but may retry |
| Seal compatibility | direct — `sera seal` already holds `task_lock`, calls `_derive_locked` | needs the same capture/re-read inside the seal lock anyway |
| Registry-lookup compatibility | registry resolved **before** `task_lock`, re-read by hash **under** `task_lock` (append-only immutable read, no registry mutation lock) — no inversion | identical requirement |
| Testability | deterministic; a probe test asserts `_derive_locked` without ownership raises | needs injected identity-mutation hooks to exercise the retry path |

Decision: **exclusive task-lock derivation.** The optimistic model (C.6) is the
documented fallback if CLI contention ever becomes a real problem; it is not
implemented now.

### C.4 Registry interaction during derivation (no lock inversion)

```text
1. resolve the selected source-registration records/hashes from
   .sera/execution-evidence-sources.jsonl with a PLAIN READ (the registry is
   append-only immutable; a read needs no registry mutation lock)   [before task_lock]
2. acquire task_lock(task_dir)
3. under task_lock, re-read each selected registration BY HASH from the same
   append-only file (still no registry_lock); verify:
     the exact record still present
     registration_hash recomputes correctly
     no same-source_id conflict line was appended
4. derive AssuranceState
5. release task_lock
```

`registry_lock` is **never** acquired while `task_lock` is held (I1-T04 rule).
The global registry ledger fingerprint is **not** consulted (spec §10.2.1); only
the exact selected hashes are.

### C.5 `AssuranceInputSnapshot` — internal immutable (test determinism only)

Not persisted; not a schema change. Captured at the start of `_derive_locked`
and threaded through every sub-derivation so one `AssuranceState` can never mix
inputs from two moments:

```text
contract_hash
task_contract_fingerprint
dynamic_task_fingerprint
active_policy_hash
route_hashes (per required stage)
repository_identity
head_sha / tree_sha
ledger_fingerprints: {task_contract, policy_snapshot, route_snapshot,
  substitution_decision, execution_target, execution_binding,
  execution_state_evidence, receipt_import, execution_receipt, review}
selected_source_registration_hashes
verification_ledger_fingerprint
seal_ledger_prefix_fingerprint
captured_at
```

Because derivation holds the exclusive lock, these values cannot change during
derivation; the snapshot exists so tests can assert "no readiness result
combined contract X with review Y that never coexisted" deterministically.

### C.6 Optimistic fallback (documented, not implemented)

```text
capture AssuranceInputSnapshot
derive state (no lock)
re-read every captured identity
  identical  → return state
  changed    → bounded retry (≤ 3); then return STATE_CHANGED_DURING_DERIVATION
```

Not mixed with the chosen model. Recorded here only so a future decision has a
concrete alternative.

### C.7 Seal interaction (updates I1-T25)

```text
sera seal:
  with task_lock(task_dir):
    state = AssuranceState._derive_locked(root, task_dir)   # no re-acquire
    require state.seal_eligibility.eligible
    capture: contract identity, selected source registrations, every bound
             non-seal evidence-ledger fingerprint, prior seal-ledger prefix fingerprint
    construct candidate SealV3 + seal_id + seal_record_hash
    re-read every captured value                            # boundary 11
    any change → SEAL_HISTORY_CHANGED (or the specific evidence reason), no append
    append exactly one line to seals.jsonl
    only then: atomically replace the optional seal.json pointer (skip if legacy v2 occupies it)
```

The selected source-registration consistency check from C.4 step 3 runs inside
this same lock; an unrelated registry append does not stale the task (spec
§10.2.1, plan §26).

## R1 §D — PLAN-004: pre-execution checkpoint ownership

### D.1 Problem restated

`sera receipt import` runs **after** execution and cannot retroactively create an
independent pre-execution observation. The parent plan's §19 boundary-7 wording
over-assigned checkpoint creation to import.

### D.2 Checkpoint authority — moved into the runner path

For executions launched through SERA's registered runner (`sera execution run`):

```text
Packet finalized (P)
  → source selected (boundary 4)
  → target T created + verified (boundary 5)
  → PRE checkpoint observed by the RUNNER  →  ExecutionStateEvidenceV1.checkpoint_before
  → execution authorized (E)
  → runner launches the external command
  → execution completes
  → POST checkpoint observed by the RUNNER →  ExecutionStateEvidenceV1.checkpoint_after
  → ExecutionBindingV1 + ExecutionStateEvidenceV1 recorded (boundary 6)
  → receipt LATER imported and VALIDATED against the pre-existing records (boundary 7)
```

`ExecutionStateEvidenceV1` already carries `checkpoint_before` / `checkpoint_after`
(spec §10.2.5) and "records the derived result of the trusted boundary" — the
runner **is** that boundary. **No schema change.** Spec §10.5: "Observed states
enter `ReceiptImportRecordV1` through the SERA/controller observation boundary
outside receipt-controlled JSON" — for runner executions that boundary is the
runner; import references, not creates.

### D.3 Receipt import responsibility (rewrites parent §19)

```text
sera receipt import:
  1. parse the hostile external receipt safely (1 MiB cap, strict bounded schema)
  2. resolve the authoritative execution_id
  3. resolve the PREVIOUSLY PERSISTED records for that execution_id:
       source registration, ExecutionTargetV1, ExecutionBindingV1,
       ExecutionStateEvidenceV1 (incl. checkpoint_before), substitution decision
  4. perform an IMPORT-TIME CURRENT observation (post-as-of-import) for currency
       — this is a NEW observation for staleness evaluation, NOT the pre-execution one
  5. compare receipt claims (input_state, output_state, hashes, verdict) to the
       pre-existing authoritative execution evidence
  6. for a builder: compare claimed output to the exact integrated/observed output
  7. for a non-mutating role: require checkpoint_before == checkpoint_after == input_state
  8. append ReceiptImportRecordV1 (references the pre-existing checkpoints; records
       the import-time observation)
```

Receipt import is a **validator of pre-existing execution evidence**, never its
historical creator.

### D.4 External executions not launched through the registered runner

```text
no trusted pre-execution checkpoint exists
  → the "before" observation is MISSING and stays missing
  → NOT synthesized from receipt.input_state, the current checkout, or a provider assertion
  → EXECUTION_STATE_EVIDENCE_MISSING
  → cannot satisfy strict runner-backed evidence
  → effective class ≤ CHECKPOINT_OBSERVED only if genuine import-side observations exist,
    else manual / legacy
  → strong class requires a separately accepted attestation mechanism (deferred — spec §10.2)
```

  `subprocess` launch; record `checkpoint_after` immediately after completion;
  both via `git_head_identity` / `ExecutionRepositoryStateV1` through the trusted
  boundary".
- **I1-T19 (state evidence):** `checkpoint_before` / `checkpoint_after` are
  populated from the runner, not import.
- **I1-T20 (receipt import):** loses "observe pre/post checkpoints"; gains
  "resolve and validate the pre-existing checkpoints; take one import-time
  current observation for currency only".
- Parent §19 boundary 7 and boundary 6 wording updated accordingly in D.2/D.3.

### A.3 Concrete Windows confinement backend

**Backend name:** `windows_appcontainer_bfs_v1`.
**Platform floor:** Windows 11 on a build where `processmodel.dll` exports and

**Dependency:** Windows OS sandbox API loaded from System32 through Python

contract and golden-buffer tests; schema/version fingerprint is part of the
registered implementation identity. Unknown sandbox-policy fields or an
unsupported OS contract fail closed rather than selecting a weaker backend.

Launch and visibility contract:

```text

   execution-scoped directories outside the governed checkout. Non-mutating T
   is a content-addressed snapshot with no `.git` indirection. Builder W is a
   self-contained isolated Git repository whose object database and refs live
   entirely inside W.
2. Stage the exact registered executable/runtime files in a content-addressed
   read-only tools directory. Never grant the user profile, repository parent,
   governed checkout, another clone/worktree, or an ambient temp directory.
3. Create a unique AppContainer identity for execution E.
4. Compile the exact sandbox policy:
     app_container = true
     fs_read_only  = [T, packet, registered tools/runtime, required OS roots]
                       for reviewer/validator/gate
     fs_read_write = [W, bounded output/receipt directory]

       the host API and verify their actual behavior in T04A; no unverified Job
       flag is part of the ENFORCED claim

       only a separately registered, policy-bound egress proxy configuration
       whose identity/fingerprint is part of the source registration
5. Launch the registered argv directly through the OS sandbox API.

   documented descendant/Job control requested by the host is separately
   recorded and verified; no child receives a full-trust broker or host path
   handle.
7. Capture OS launch result, process identity, sandbox-policy hash, target/W
   directory file identities, denial-test results, completion, and post-state.
```

The OS boundary, not pathname secrecy, prevents the original checkout and
alternate host repositories from being opened. Repository paths outside the
explicit BFS grants are denied. For a non-mutating stage, T is read-only. For a
builder, only W is repository-writable; T stays read-only and is revalidated.
Unexpected files, nested repository metadata, reparse points, or output outside
the contract invalidate the binding. Network access, when explicitly enabled
through the bound proxy, remains a disclosed non-repository-data limitation and
does not become provider identity or authorship evidence.

A linked `git worktree` is forbidden as confined builder W because its `.git`
file points into the governed repository's common object store. Builder
derivation is instead:

```text
host creates fresh W with a private .git directory
host imports only exact commit A and its reachable history into W without
  alternates, hardlinks, shared object stores, or path indirection
host checks out detached A
host verifies W HEAD/tree/change fingerprint == A/clean and scans .git config
  for alternates, external worktree pointers, hooks, and unexpected remotes

```

After the builder commits B', the host validates `B'^ == A`, the exact commit,
tree, task-change fingerprint, scope, and clean residual state. It imports B'

observes governed commit/tree equality. Any alternate/shared object store,
unexpected remote, non-A parent, moved governed HEAD, or rewritten/cherry-picked
SHA fails closed.

The verified property is deliberately narrow:

```text

filesystem access; the only exposed repository input was exact T(A/P), or W(A)
```

It does not prove provider identity, authorship, reasoning quality, absence of
permitted network data, or resistance to a local administrator controlling the

## R2 §C — GIR-003: two-phase AssuranceState derivation and ownership guard

### C.1 APIs and objects

```text
prepare_assurance_inputs(root, task_dir) -> PreResolvedGlobalInputs

task_lock(task_dir) -> context manager yielding TaskLockGuard

AssuranceState.derive(root, task_dir) -> AssuranceState

AssuranceState._derive_locked(
    root,
    task_dir,
    guard: TaskLockGuard,
    global_inputs: PreResolvedGlobalInputs,
) -> AssuranceState
```

`prepare_assurance_inputs` performs no readiness decision and acquires no task
mutation authority. It strictly reads enough task-local immutable references to
identify the bounded candidate set of selected source-registration hashes,
reads and validates those exact records from the append-only global registry,
and returns immutable `PreResolvedGlobalInputs` containing the candidate hash
set, canonical registration records, source-ID conflict scan result, registry
prefix observation, and preparation timestamp.

It may take and release `registry_lock` while reading the registry because no
task lock is held. A task-local read that observes an in-progress mutation or a
registry read that observes an incomplete append is `PREPARATION_UNSTABLE` and
uses the same bounded retry; it is never normalized by skipping a line.

`TaskLockGuard` is an in-memory, non-serializable object constructible only by
the private successful lock acquisition path. It contains an unguessable random
token, normalized task path, acquisition timestamp, owner pid/thread diagnostics,
and `active`. The lock context marks `active = false` before release. The class
uses a private module sentinel/capability so merely fabricating a dataclass with
matching fields is rejected. No guard field is assurance evidence.

The guard is an internal correctness capability against accidental or
cross-task API misuse, not a security boundary against malicious code already
executing inside the trusted SERA process. The filesystem lock remains the
cross-process exclusion primitive.

`_derive_locked` rejects no guard, inactive guard, wrong-task guard, fabricated
guard, or a guard not registered as the active guard in the current process.
It never infers ownership from `.lock/` existence.

### C.2 Public and locked flows

```text
AssuranceState.derive(root, task_dir):
  for attempt in range(3):
    global_inputs = prepare_assurance_inputs(root, task_dir)
    with task_lock(task_dir) as guard:
      result = _derive_locked(root, task_dir, guard, global_inputs)
      if result is SELECTION_CHANGED:
        continue after releasing task_lock
      return result
  raise AssuranceStateChangedDuringDerivation
```

Under the task lock, `_derive_locked` first derives the actual active task-local
selected hash set from the current contract/policy/route/evidence selection. It
requires exact set/order equality with `global_inputs`. It then re-reads the
exact registry records by hash without `registry_lock`, validates hashes and
records, scans for same-source-ID conflicts, and compares the re-read canonical
records with the prepared records. A selection mismatch requests a bounded
retry; missing/invalid/conflicting selected records fail closed. Unrelated
append-only registrations neither join the selected set nor stale the task.

Only after this reconciliation does `_derive_locked` capture the complete
`AssuranceInputSnapshot` and derive all fields from it while still holding the
exclusive task lock. No `task_lock → registry_lock` path exists.

Seal uses the same pre-resolution and guard:

```text
global_inputs = prepare_assurance_inputs(root, task_dir)
with task_lock(task_dir) as guard:
  state = AssuranceState._derive_locked(root, task_dir, guard, global_inputs)
  require state.seal_eligibility
  capture and revalidate all seal-bound inputs
  append Seal v3
```

Seal never calls public `derive()` and never re-enters the lock. A selection
change returns before append and restarts the whole pre-resolution/lock flow,
bounded to three attempts. Immediately before Seal append it again re-reads the
selected records by exact hash and checks same-source conflicts without taking
`registry_lock`; a changed or incomplete registry view aborts the append.

Tests cover equal pre/under-lock selection, one selection change then success,
continuous change then bounded failure, selected-source conflict, unrelated
registry append, missing/inactive/wrong-task/fabricated guard, guard invalidation
on context exit, seal reuse without deadlock, derive waiting for a mutator, and
a mutator waiting for derive. No result may combine task-local evidence from
different snapshots.

## R2 §D — GIR-004: durable PRE before process launch

### D.1 Approved staged evidence model

The locked `ExecutionStateEvidenceV1` schema permits optional
`checkpoint_before`/`checkpoint_after`; `execution_binding_hash` is required
only for enforced or attested evidence; and modern checkpoint observations use
the built-in controller registration. Therefore PRE is a separate immutable
checkpoint-class `ExecutionStateEvidenceV1` record, not a new schema and not a
partially written future enforced record.

PRE record:

```text
evidence_id: fresh UUIDv4
task/execution/stage/target/packet/policy/route/expected_state: exact authorized context
source_id/source_registration_hash: built-in controller checkpoint registration
claimed_evidence_class: CHECKPOINT_OBSERVED
effective_evidence_class: CHECKPOINT_OBSERVED
source_capability_ceiling: CHECKPOINT_OBSERVED
verification_method: controller_pre_execution_checkpoint_v1
execution_binding_hash: absent
binding_verification_result: INDETERMINATE
checkpoint_before: observed A
checkpoint_after: absent
source_evidence_hash: hash of the canonical controller observation
limitations: [pre_checkpoint_only, execution_not_yet_started]
observed_at: before launch
```

After execution, binding verification and POST produce a second immutable
`ExecutionStateEvidenceV1` with a fresh evidence ID. It resolves the unique
valid PRE record for the same complete context, copies its exact
`checkpoint_before`, adds `checkpoint_after`, and, only for a VERIFIED sandbox
binding, carries `execution_binding_hash` and a derived effective ENFORCED
class. Its `source_evidence_hash` domain-separates and hashes the PRE evidence
hash, POST observation hash, and binding hash. The PRE record is never mutated.
Multiple PRE candidates, conflicting context, missing PRE, or a PRE created
after launch prevents strong evidence.

### D.2 Launch ordering and crash behavior

`sera execution run` uses one exclusive task lock across the authorization
boundary and supervised process lifetime:

```text
prepare source registration before task_lock
acquire task_lock as TaskLockGuard
revalidate source/contract/policy/route/packet/target and workspace pre-state
capture + canonicalize PRE
append complete PRE ExecutionStateEvidenceV1 line
flush + best-effort fsync; append failure aborts
confirm the appended record is strictly readable by hash
authorize launch
launch sandboxed process while task_lock remains held
observe completion or timeout
capture POST and verify binding
re-read the exact selected source registration and same-source conflict state
append binding/final evidence/failure history as applicable
release task_lock
```

Holding the lock prevents task-local authorization state from moving between
durable PRE and launch. The runner attempts documented host-supported
kill-on-controller-close/descendant controls and T04A verifies actual behavior;
PRE durability and the ENFORCED classification do not assume those controls. A normal
process failure or timeout still appends failure/completion history and leaves
PRE untouched. A runner crash may leave no POST/final record and may leave the
fail-closed lock directory, but the already flushed PRE remains authoritative
historical checkpoint evidence. Recovery reports an incomplete execution; it
does not synthesize POST, reuse PRE for a later execution ID, or rewrite PRE.

Receipt import resolves the original PRE and final evidence by complete
execution context, validates the receipt against them, and records an
import-time currency observation. It cannot create, replace, or upgrade PRE.

Tests prove the PRE append and strict re-read complete before a launch hook can
fire; append/fsync/readback failure prevents launch; process failure, timeout,
and simulated runner termination preserve PRE; POST absence is explicit;
failed execution cannot rewrite PRE; later import resolves the original PRE;
and both timestamp order and instrumented append-before-launch order hold.

### A.1 Policy result

`policy_result` is derived from the active task-bound policy's treatment of the
exact built-in controller registration and checkpoint role. SERA creating the
record does not imply acceptance:

```text
policy accepts C for this checkpoint role → policy_result = accepted
policy does not accept C for this role     → policy_result = rejected
```

A rejected record can remain structurally valid immutable checkpoint history.
It is insufficient for a strong stage requirement and is never upgraded by a
later binding or receipt. `rejected` means policy-ineligible, not malformed.

### A.2 Two distinct hashes

The controller observation hash is:

```text

    target_hash,
    target_id,
    task_id
  })
```

the same record/context. `expected_state_hash` is the already specified
domain-separated canonical hash of `ExecutionRepositoryStateV1`; observed state
is the exact canonical `checkpoint_before` object.

The record identity follows the locked rule without a PRE-specific domain or
extra exclusion:

```text
evidence_hash = SHA256(
  canonical_json(complete ExecutionStateEvidenceV1 excluding only evidence_hash)
)
```

`source_evidence_hash` identifies the controller observation input.
`evidence_hash` identifies the complete normative evidence record, including
policy result, limitations, and source evidence hash. They are never
interchangeable.

### A.3 Durable append/readback gate

```text

→ build and strict-validate the complete record above
→ calculate evidence_hash
→ append one complete canonical JSONL line under task_lock

→ recompute evidence_hash
→ require exact task/execution/stage/target/state/packet/policy/route/source equality
→ only then authorize and launch the process
```

Missing/invalid fields, append failure, unreadable/truncated history, hash
mismatch, context mismatch, or readback failure means **DO NOT LAUNCH**. Timestamp
order alone never satisfies this gate.
