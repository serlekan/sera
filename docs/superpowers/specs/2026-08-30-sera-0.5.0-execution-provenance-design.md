# SERA 0.5.0 Execution Provenance and Governed Dispatch Design

**Status:** Approved design, implementation not started
**Date:** 2026-08-30
**Release:** SERA 0.5.0
**Self-hosting task:** `20260830T034346Z-sera-0-5-0-execution-provenance`

## 1. Purpose

SERA 0.5.0 closes the gap between a declared route and the evidence that a
specific execution actually occurred. The release binds task policy, repository
identity, packet input, observed execution identity, output, verdict, review,
verification, and seal without introducing native provider invocation.

The governing rule is:

> SERA must never claim stronger assurance than the evidence it actually possesses.

The architectural dependency is fixed:

```text
provenance foundation -> evidence integrity -> reporting and release
```

The work is delivered as three independently reviewable increments. Each
increment leaves the repository valid and testable. A later commit makes an
earlier increment review historical; no increment review substitutes for the
fresh final release review and gate.

## 3. Scope and non-goals

### 3.1 In scope

- versioned execution receipts and import records;
- canonical execution roles and implementation origin;
- immutable policy and route snapshots;
- provider/model substitution governance;
- receipt validity, currency, uniqueness, and replay protection;
- one authoritative derived `AssuranceState`;
- versioned verification history;
- structural reviewer packets and lint evidence;
- deterministic context reduction and overflow manifests;
- repository knowledge fingerprints;
- `sera explain` and `sera report`;
- conservative compatibility and migration;
- seal v3 and exact-state self-hosted release evidence.

### 3.2 Not in scope

- direct OpenAI, Anthropic, Gemini, or other provider invocation;
- provider-specific SDK dependencies in the core package;
- a database or generic event-store rewrite;
- cryptographic claims that an external provider or person performed work when
  SERA only possesses a local assertion;
- automatic rewriting, deletion, or strengthening of historical evidence;
- automatic silent policy adoption after configuration changes;
- repair of the seven unrelated baseline lint errors.

## 4. Architecture

### 4.1 Domain modules

New assurance semantics live in focused modules. `core.py`, `controller.py`, and
`cli.py` remain compatibility and orchestration facades; they are not hidden
sources of truth for new readiness rules.

| Module | Responsibility |
| --- | --- |
| `schemas.py` | Schema constants, bounded strict JSON readers, canonical serialization, ledger fingerprints, compatibility classification. |
| `provenance.py` | Canonical roles, implementation origin, repository identity, policy/route snapshots, receipt import, receipt validation, substitution decisions, independence checks. |
| `verification.py` | Verification attempt v2 capture, append-only storage, environment/dependency identity, derived history findings. |
| `knowledge.py` | Contained knowledge-source discovery, symlink/root escape prevention, immutable hashes. |
| `packets.py` | Typed packet model, packet v4 bindings, lint records, deterministic reduction and overflow manifests, rendering. |
| `assurance.py` | Authoritative derived `AssuranceState`, sequencing, seal eligibility, reason codes. |
| `reporting.py` | Text, Markdown, and JSON transformations of state and evidence; no readiness decisions. |

Dependencies flow toward domain modules. `assurance.py` consumes normalized
records from the other domain modules. `reporting.py` consumes
`AssuranceState`; it never imports controller readiness helpers. Domain modules
must not import `cli.py` or `controller.py`.

### 4.2 External execution boundary

```text
typed packet
  -> external controller or future adapter
  -> raw output plus ExecutionReceipt v1
  -> hostile-input-safe receipt import
  -> intrinsic and binding validation
  -> currency evaluation
  -> stage evidence
  -> AssuranceState
```

A future native adapter must use this same import and validation boundary. It
does not receive a privileged path and cannot weaken provenance semantics.

## 5. Canonical serialization and immutable ledgers

All new persisted records contain an integer `schema_version`. Strict readers
reject missing, Boolean, non-integer, negative, and unsupported versions.

Canonical JSON is UTF-8 JSON with:

```text
sorted object keys
no insignificant whitespace
Unicode preserved rather than ASCII escaped
finite JSON values only
arrays preserved in declared order
```

Ledger fingerprints are semantic and order-sensitive:

1. Strictly parse every non-empty line. A malformed line blocks assurance; it
   is never skipped.
2. Normalize the record through its schema or explicit compatibility reader.
3. Canonically serialize each normalized record.
4. Hash each record with SHA-256.
5. Hash a domain separator, schema family, record count, and the ordered
   sequence of `index`, NUL separator, and record hash.

This makes ordering, duplicate records, appended records, and field mutations
observable while making platform newline style and insignificant JSON spacing
irrelevant. Ledger writes are append-only. No API updates or removes a record.
This rule applies to every assurance ledger, including Seal v3 history. Ordinary
operation MUST NOT rewrite, replace, delete, or omit a previously persisted
record merely because newer or cleaner evidence exists. A malformed or
incomplete final JSONL record blocks modern assurance and is not silently
ignored.

Task-scoped mutating operations use a cross-platform atomic lock directory under
the task runtime directory. Lock acquisition failure is closed. SERA does not
silently remove a lock it cannot prove is stale. A record is serialized and
written as one UTF-8 append while the lock is held.

legacy v2 `seal.json` remains evidence at its historical location and is
distinguished by its schema rather than treated as a ledger entry.

## 7. Task v2, repository identity, and knowledge identity

### 7.1 Task v2 additions

Task v2 retains existing fields and adds:

```text
implementation_origin: sera_builder | external | pre_existing
repository_identity: RepositoryIdentityV1
active_policy_hash: sha256
knowledge_sources: ordered KnowledgeSourceV1[]
knowledge_fingerprint: sha256
provenance_class: modern | legacy
```

New implementation tasks default to `sera_builder`. Importing or validating
already-existing work requires an explicit `external` or `pre_existing` origin.
Compatibility reads of task v1 use `pre_existing` and `legacy` internally; they
do not claim a routed builder authored historical changes.

Increment 1 creates task v2 before knowledge discovery is implemented. During
that increment, `knowledge_sources` is an empty ordered list and its fingerprint
is the canonical empty-collection fingerprint, explicitly reported as
`unassessed_by_pre_increment_2_runtime`. Increment 2 begins populating the same
v2 fields for newly created or explicitly re-contracted tasks without another
task schema change. Existing Increment 1 tasks retain their historical empty,
unassessed snapshot unless an explicit policy-adoption event creates a new task
contract. An empty list never implies that a repository has no governing
knowledge.

### 7.2 RepositoryIdentityV1

HEAD and tree do not distinguish all logical repositories. Task and receipt
bindings therefore include a logical repository identity snapshot:

```text
schema_version: 1
strategy: configured | git_remote_root | local_git_dir
logical_id: sha256
strength: configured | derived | local_only
components: bounded non-secret diagnostic hashes/identifiers
```

Resolution order:

1. `configured`: an explicit non-secret repository ID in config v2. `sera init`
   generates it once. It may be committed as policy.
2. `git_remote_root`: SHA-256 of canonical, credential-stripped sorted remote
   identities plus the immutable root commit.
3. `local_git_dir`: SHA-256 of the resolved Git common-directory identity and
   root commit, reported as `local_only`.

Remote canonicalization removes usernames, passwords, query strings, and
fragments before hashing. Raw credential-bearing URLs are never persisted.

This identity proves only that SERA compared the same recorded logical
identifier and components. It is not a signature, ownership proof, or defense
against a malicious actor who copies the repository ID and all task state.
Reports expose its strategy and strength.

### 7.3 KnowledgeSourceV1

Each source records:

```text
schema_version: 1
path: normalized repository-relative path
sha256: content hash
bytes: non-negative integer
source_class: repository | workspace | product
```

Discovery accepts only configured relative paths. It rejects absolute paths,
empty paths, `..` traversal, resolved paths outside the repository, symlink
escapes, non-regular files, unreadable files, and files over the configured
limit. Paths are sorted by normalized path before fingerprinting. The knowledge
fingerprint is part of task contract identity. Legacy tasks receive no
retroactive knowledge entries.

## 8. Immutable policy and route snapshots

### 8.1 Configuration v2

Config v2 adds provider-neutral stage policies for the four canonical roles,
provenance requirements, legacy behavior, repository identity, knowledge
sources, context limits, and substitution rules. Config v1 lanes are accepted
through a compatibility translator. Compatibility aliases terminate there.

### 8.2 PolicySnapshotV1

A task policy snapshot contains only normalized policy relevant to that task:

```text
schema_version
task_id
captured_at
trigger: task_created | ownership_confirmed | explicit_policy_adoption
mode and risk
required stages
implementation-origin rules
provenance-strength requirements
legacy override, if any
substitution rules
independence requirements
verification requirements
context budgets
knowledge policy
repository identity requirement
snapshot_hash
```

The hash excludes only its own `snapshot_hash` field. The task references the
active snapshot hash. Current configuration is not used to reinterpret a
historical execution.

Ownership confirmation appends a new policy snapshot because it may alter risk
and routing. Other configuration changes do not alter an active task. Explicit
adoption uses a task policy command requiring actor and reason and appends a new
snapshot. Adoption invalidates packets and downstream current evidence through
the new policy hash; it does not rewrite old snapshots.

### 8.3 RouteSnapshotV1

Every packet binds a route snapshot containing:

```text
schema_version
task_id
canonical stage
policy_hash
primary requested provider/model
ordered approved fallbacks
required identity-evidence class
required output/verdict fields
snapshot_hash
```

Receipts bind both policy and route hashes. Changing current configuration
cannot retroactively approve a substitution.

## 9. Canonical roles and implementation origin

Internal roles are exactly:

```text
implementation_builder
implementation_validator
independent_reviewer
release_gate
```

`builder`, `independent`, and `gate` are input aliases only. Persisted modern
records and domain functions use canonical roles.

Origin semantics:

- `sera_builder`: policy may require a current valid builder receipt.
- `external`: policy may require a validator receipt but must report that SERA
  cannot prove who authored the implementation.
- `pre_existing`: policy may require validation of existing work and reports no
  builder-origin claim.

An `implementation_validator` receipt never satisfies an
`implementation_builder` requirement. Distinct role labels alone do not prove
distinct actors.

## 10. ExecutionReceiptV1

### 10.1 Required receipt fields

```text
schema_version: 1
task_id
stage: canonical role
requested_provider
requested_model
actual_provider
actual_model
identity_evidence
adapter, optional
execution_id
started_at
completed_at, optional
exit_status
repository_identity
head_sha
tree_sha
task_fingerprint
policy_hash
route_hash
input_packet_hash
raw_output_hash, required for successful counted stages
parsed_verdict, required for reviewer and gate success
substitution, required when requested and actual targets differ
metadata, optional bounded object
```

`identity_evidence` records a provider-neutral class:

```text
provider_attested
adapter_observed
controller_observed
manual_assertion
unknown
```

It also contains an observer identifier and evidence hash when available. A
requested target copied into actual fields is not strong identity evidence.
Policy decides which classes may count. SERA reports the evidence class and its
limitations; it never relabels manual assertions as provider attestation.

All receipt fields are untrusted. A plain JSON file supplied to the CLI cannot
establish an identity-evidence class stronger than `manual_assertion`, regardless
of the class written inside that file. A stronger class requires a separately
registered verifier or observer implementation whose result enters the domain
API outside receipt-controlled JSON. SERA 0.5.0 core ships no provider-specific
attestation verifier. The interface exists for external and future adapters, but
absence of such a verifier remains an explicit limitation rather than an
optimistic identity claim.

### 10.2 Exit states

```text
success
failed
cancelled
quota_exceeded
provider_error
unknown
```

Only `success` can satisfy a completed stage. All other states remain history.

### 10.3 Receipt import records

The receipt importer accepts a path as input but never derives a storage path
from receipt-controlled values. Each attempt appends `ReceiptImportRecordV1`
with import ID, received time, raw SHA-256, raw byte count, parse status, target
task, and reason codes. Raw hostile input is not copied into the ledger.

Structurally safe receipts are canonicalized and appended to
`execution-receipts.jsonl` even when they later fail task, repository, policy,
route, packet, substitution, or currency checks. Malformed or oversized input is
represented by the import record and its hash rather than unsafe raw content.

The conceptual lifecycle is:

```text
RECEIVED -> VALIDATED
RECEIVED -> REJECTED
VALIDATED + current repository movement -> STALE for current assurance
```

Receipt validity and receipt currency are separate. A receipt validly describing
execution against HEAD A remains historical valid evidence after HEAD moves to
B, but it is stale and cannot advance assurance for B.

### 10.4 Hostile-input limits

Before JSON parsing, receipt input is limited to 1 MiB. After parsing:

- the top level must be an object;
- unknown top-level fields are rejected;
- required strings are non-empty and at most 4,096 characters;
- provider, model, stage, status, hashes, IDs, and timestamps have tighter
  field-specific limits;
- hashes are lowercase 64-character hexadecimal SHA-256 values;
- timestamps are timezone-aware ISO 8601 values;
- metadata is at most 32 keys, depth 4, 64 KiB canonical JSON, with scalar or
  bounded list/object values;
- path-like metadata keys and control characters are rejected;
- non-finite numbers are rejected;
- execution IDs are data, never filenames or commands.

Receipt import performs no shell interpolation and invokes no provider command.

### 10.5 Output binding

Successful stage evidence requires a raw output hash. Receipt import accepts an
explicit output file, reads it without following a final symlink, applies the
configured size limit, computes SHA-256, and compares it with the receipt. A
mismatch or missing required output is retained but unusable.

Verified raw output is stored only in excluded task runtime storage under a
content-addressed hash. It is absent from packets and reports. Receipt metadata
must not contain secrets or raw output. Reports expose hashes and sizes only.

## 11. Receipt validation, replay, and conflicts

Validation is ordered and machine-readable:

1. schema and bounded type validation;
2. duplicate/conflict validation;
3. task and logical repository binding;
4. canonical stage and implementation-origin policy;
5. task fingerprint, policy, and route binding;
6. packet hash and output hash binding;
7. requested/actual provider-model and substitution policy;
8. identity-evidence strength;
9. execution outcome and stage-specific fields;
10. independence and sequencing prerequisites;
11. current HEAD/tree currency.

Replay behavior:

- same execution ID and same receipt hash: the repeated import is rejected as a
  duplicate; the original receipt remains eligible;
- same execution ID and different receipt hash: all receipts using that ID are
  conflicting and unusable;
- receipt from another task, logical repository, policy, route, or packet:
  rejected for binding mismatch;
- valid receipt for the correct historical packet after HEAD/tree movement:
  valid but stale, not fraudulent;
- a gate receipt produced while independent review was stale is retained but
  unusable for current gate assurance.

## 12. Provider/model substitution

Classifications are exactly:

```text
APPROVED_FALLBACK
MANUAL_SUBSTITUTION
UNAPPROVED_SUBSTITUTION
```

When requested and actual targets differ, immutable substitution evidence must
contain requested target, actual target, classification, reason, actor, decision
timestamp, and policy result. Classification is verified against the bound
policy and route snapshots rather than trusted from the receipt.

- An actual target in the route's ordered fallback list may be
  `APPROVED_FALLBACK`.
- `MANUAL_SUBSTITUTION` counts only when the bound task policy explicitly
  authorizes manual override and the complete decision evidence exists.
- Any other difference is `UNAPPROVED_SUBSTITUTION` and fails closed in strict
  assured mode.

Historical provider identity is never rewritten after substitution.

## 13. Structural independence

SERA tests only observable dimensions. A counted independent review must have:

- canonical stage `independent_reviewer`;
- a receipt hash distinct from implementation and validator receipts;
- an execution ID not used by another stage;
- a separate review record bound to that receipt;
- all policy-required actor/controller, provider, model, or adapter differences;
- a current task, repository, packet, policy, route, output, and verdict binding.

Policy may require cross-provider, cross-model, distinct observer, or distinct
actor metadata. Missing required dimensions block assurance. Without such
evidence SERA may prove only that a distinct receipt and stage were recorded; it
cannot prove absence of collusion or that a human/model unquestionably performed
the review.

The release gate likewise requires a distinct execution ID and receipt. It may
share a provider or model only when the bound policy allows it.

## 15. Verification attempt v2

Each attempt records:

```text
schema_version: 2
attempt_id
command
cwd: normalized repository-relative path
started_at
completed_at
exit_code
repository_identity
head_sha
tree_sha
task_fingerprint
policy_hash
environment: os, environment_class, runtime_versions
dependency_lock_hash, optional
stdout_hash
stderr_hash
stdout_bytes
stderr_bytes
attempt_number
```

Commands come from the task policy, not receipt or repository text. Existing
shell behavior remains compatibility-sensitive; no receipt field becomes a
command. Output remains in local runtime logs and only hashes/sizes enter the
ledger.

Attempt number is per exact command string in ledger order. Dependency identity
hashes the sorted set of configured lockfiles with path and content hash.
Environment identity is a canonical hash of environment class, OS, and recorded
runtime versions.

Derived non-fatal findings are:

```text
PASS_AFTER_FAILURE
ENVIRONMENT_CHANGED
DEPENDENCY_CHANGED
RERUN_WITHOUT_CODE_CHANGE
```

Evaluation distinguishes same command/same tree/same environment, same
command/same tree/changed environment, and same command/changed tree. Policy may
promote a finding to blocking; the default surfaces it without erasing or
invalidating successful evidence.

Legacy unversioned attempts remain readable but carry `LEGACY_PROVENANCE` and no
invented environment or repository fields.

## 16. Structural packet model and packet provenance v4

### 16.1 Typed sections

Packet v1 is a JSON model rendered to Markdown. Section kinds are:

```text
OBJECTIVE
INVARIANT
CLAIM
MACHINE_EVIDENCE
CHANGED_FILES
OWNED_FILES
TEST_RESULT
PREVIOUS_FINDING
QUESTION
```

Each section records kind, stable section ID, source/attribution, priority,
content or structured items, and estimated tokens. Markdown headings are a
presentation of this model, not the type system.

### 16.2 Packet lint

Lint emits versioned structured findings without rewriting source content.
Unsupported controller assertions such as “verified implementation”, “fully
compliant”, “secure”, “production-ready”, or “all tests prove correctness” are
flagged when present in controller-authored claims. Attributed machine evidence,
quoted task text, and prior findings are preserved and labeled.

Blocking lint prevents packet dispatch according to policy. Findings persist in
`packet-lint.jsonl` and bind to packet hash.

### 16.3 Packet v4 bindings

Packet provenance v4 binds:

```text
task ID and task fingerprint
logical repository identity
HEAD and tree
policy hash
route hash
canonical stage
canonical packet-model hash
rendered Markdown hash
knowledge fingerprint
context manifest hash
review change fingerprint and coverage, when applicable
```

Both the structural JSON and rendered Markdown are validated before dispatch.
The receipt's `input_packet_hash` is the canonical packet-model hash.

## 17. Deterministic context reduction

Context selection is deterministic for the same repository, task, policy,
packet stage, and budget. Ranking order is:

1. mandatory semantic section class;
2. stage priority;
3. explicit inclusion;
4. changed-file status;
5. owned-file status;
6. dependency distance;
7. relevance score descending;
8. estimated tokens ascending;
9. normalized path or stable section ID lexicographically.

Mandatory retained semantic classes are task objective, safety/security
invariants, acceptance criteria, and relevant unresolved findings. They are
retained before optional source context.

When estimated context exceeds budget, SERA emits a reduced packet and a
versioned overflow manifest listing configured budget, original estimate,
selected items, excluded items, token estimates, and deterministic reasons.
Changed-file review evidence retains existing complete-coverage guarantees. If
minimum evidence for every changed file or one mandatory semantic item cannot
fit, generation fails with a specific reason rather than truncating silently.

## 18. AssuranceState

### 18.1 Single authority

`AssuranceState` is the sole readiness authority for `next`, `check`, `seal`,
`explain`, and `report`. Controller and CLI layers format its results but do not
recompute them.

The state includes:

```text
task and policy identity
repository identity and current HEAD/tree
verification status and findings
implementation origin and provenance status
independent review status
release gate status
seal eligibility and seal currency
legacy provenance status
ordered reason codes and required next actions
```

Stage statuses are:

```text
MISSING
CURRENT
STALE
FAILED
BLOCKED
LEGACY
```

Receipt evaluation additionally distinguishes intrinsic/binding validity from
current-state currency.

### 18.2 Sequencing

The ordering is fail-closed:

```text
scope and task identity
policy and route identity
implementation builder or validator requirement
verification
independent review
release gate
seal
```

A stale or failed independent review blocks gate assurance before a gate result
can count. A gate receipt created anyway remains history with gate status
`BLOCKED` and the independent-review reason. HEAD or tree movement makes review,
gate, and seal evidence stale for current assurance.

## 19. TOCTOU checkpoints

Repository identity is checked at six mandatory boundaries:

1. **Packet preparation:** capture logical repository/HEAD/tree before reading
   task context and after writing packet artifacts. Movement aborts dispatchable
   packet creation.
2. **Receipt import:** compare receipt with immutable packet bindings and capture
   current identity before and after the locked append. The receipt is retained;
   movement prevents current classification.
3. **Receipt validation:** validate intrinsic fields and historical bindings
   independently from current HEAD/tree currency.
4. **Review recording:** verify receipt, prerequisites, packet, and current
   identity before and after appending the review record.
5. **Gate recording:** perform the review checks plus require a current accepted
   independent review at both checks.
6. **Seal generation:** under the task mutation lock, derive state, all bound
   non-seal evidence fingerprints, and the pre-append seal-ledger fingerprint;
   construct the candidate; then re-read every bound value immediately before
   appending exactly one record to `seals.jsonl`. Any movement fails before the
   append. Only after the authoritative append completes may SERA atomically
   replace the optional derived `seal.json` pointer. Pointer failure never
   rewrites or removes the appended record.

Mandatory scenario:

```text
HEAD A -> packet A -> external execution -> HEAD B -> receipt A
```

Result: receipt A is retained and may be intrinsically valid for packet A, but
is stale relative to B and cannot advance current assurance.

## 20. Seal v3

### 20.1 Authority, identity, and bindings

`seals.jsonl` is the authoritative persisted Seal v3 history. Seal v3 records
are append-only historical evidence. SERA MUST NOT update, replace, delete, or
rewrite a previously persisted Seal v3 record during ordinary operation. Every
successful modern sealing operation appends exactly one record. A later seal
does not supersede history by removal; it adds another historical observation.

Each Seal v3 record contains:

```text
schema_version: 3
seal_id
SERA version
task ID and fingerprint
logical repository identity
sealed HEAD and tree
implementation origin
active policy hash
knowledge fingerprint
ordered evidence-ledger fingerprints
AssuranceState fingerprint
required and satisfied stages
sealed_at
prior_seal_ledger_fingerprint
seal_record_hash
```

Evidence collection fingerprints cover policy snapshots, route snapshots,
receipt imports, execution receipts, verification, reviews, packet lint, and
any other collection that influenced readiness. Filenames are diagnostics, not
identity. Appending a duplicate or failed record after sealing changes the
relevant ledger fingerprint and makes the seal stale, even when current stage
selection remains successful.

`prior_seal_ledger_fingerprint` is the canonical ledger fingerprint of the
complete authoritative `seals.jsonl` prefix as it existed before this record
was appended; a missing ledger uses the schema-defined empty-ledger
fingerprint. The field binds prior seal history without requiring a record to
hash a ledger that already contains itself. The ordered evidence-ledger map in
the record binds only assurance-relevant non-seal collections that existed
before append.

`seal_id` is a lowercase UUIDv4 generated once while the task mutation lock is
held and is unique within a task's seal ledger. It identifies one logical seal;
it is not an authentication claim. Reuse of a `seal_id` with different content
is a conflict. The stable record identity is computed exactly as:

```text
seal_record_hash = SHA256(canonical SealV3 record excluding seal_record_hash)
```

No other field is excluded. The hash uses the canonical JSON rules in Section
5 and lowercase hexadecimal encoding.

### 20.2 Seal-ledger validation and current selection

`seals.jsonl` follows Section 5. Append order is authoritative. Readers MUST
parse the complete ledger and validate every record, including its schema,
record hash, task/repository binding, unique identity, and
`prior_seal_ledger_fingerprint` against the actual prefix. Malformed or
truncated lines block assurance, including an incomplete final line. Record
reordering, deletion, mutation, or insertion changes the ledger fingerprint;
normalization MUST NOT make any record disappear. Platform newline style and
insignificant JSON whitespace are non-semantic after normalization.

An exact duplicate record remains present and observable, changes the ledger
fingerprint, produces `SEAL_RECORD_DUPLICATE`, and blocks strict assured seal
acceptance until the duplicate is explained through an explicit immutable
policy decision. The duplicate is never deleted during ordinary operation. The
same `seal_id` with different content produces `SEAL_RECORD_CONFLICT` and
`SEAL_HISTORY_CONFLICT` and fails closed.

Seal validity and seal currency are separate. Historical validity asks whether
the record was structurally valid, internally consistent, properly bound to
the ledger prefix, and eligible for the state it sealed. Currency compares
those preserved bindings with the current task, repository, HEAD/tree, policy,
knowledge, and non-seal evidence state. A historically valid seal can therefore
be `STALE` without being fraudulent.

Current-seal selection MUST:

1. parse the complete seal ledger;
2. validate all records and prefix relationships;
3. derive each record's historical validity;
4. compare each valid candidate with current task, repository, and evidence
   state;
5. select the newest eligible `CURRENT` record according to ledger order; and
6. fail `sera check --require-seal` closed with an explicit reason when no
   current record exists.

Historical stale, failed, and non-current records remain inspectable. The last
physical line is not trusted merely because it is last.
An absent `seals.jsonl` produces `SEAL_HISTORY_MISSING`; an empty ledger has no
current seal and likewise cannot satisfy `--require-seal`.

For the sequence `HEAD A -> verification A -> review A -> gate A -> seal A`,
followed by implementation change and the complete assurance sequence for
`HEAD B -> seal B`, the authoritative ledger contains record 1 for A and record
2 for B. Both remain inspectable; A is historically valid but `STALE` for B,
and B is `CURRENT`. No replacement occurs. Likewise, appending a verification
attempt after seal A changes the bound verification-ledger fingerprint and
makes A stale even if HEAD/tree did not move. A new seal requires the full
current policy-defined assurance process; SERA MUST NOT mutate A.

### 20.3 Sealing algorithm and current pointer

`sera seal` performs the following conceptual algorithm:

1. acquire the task mutation lock;
2. derive the single authoritative `AssuranceState` and require seal
   eligibility;
3. capture task/repository identity, HEAD/tree, policy, knowledge, every bound
   non-seal evidence-ledger fingerprint, and the prior seal-ledger fingerprint;
4. construct canonical Seal v3, generate its `seal_id`, and compute
   `seal_record_hash`;
5. re-read repository identity, HEAD/tree, every bound evidence fingerprint,
   and the complete prior seal-ledger state;
6. if any captured value changed, fail with `SEAL_HISTORY_CHANGED` or the more
   specific evidence reason without appending;
7. append exactly one canonical Seal v3 line to `seals.jsonl` and complete the
   append using the repository's supported persistence primitive;
8. only after successful append, optionally atomically update the derived
   `seal.json` current pointer; and
9. release the lock.

Append occurs under the task lock. SERA reports append success only after the
platform write operation completes, but makes no durability claim beyond the
guarantees of the operating system and filesystem abstraction it actually
uses. A crash or partial append that leaves malformed/truncated JSONL blocks
modern assurance; readers MUST NOT ignore the final record.

The optional 0.5.0 `seal.json` pointer contains enough identity (at minimum
schema version, `seal_id`, `seal_record_hash`, and post-append seal-ledger
fingerprint) to compare it with the authoritatively derived current record. It
is optional, derived, non-authoritative, replaceable, and reconstructable.
Deleting it does not delete seal history. Changing it does not change
authoritative history. A missing pointer may be regenerated. An inconsistent
pointer produces `SEAL_POINTER_MISMATCH` and MUST fail validation or be
regenerated; it never overrides the ledger.

If authoritative append succeeds but pointer update fails, the Seal v3 record
remains successfully recorded and all earlier records remain unchanged. The
command reports a recoverable pointer-update error such as “seal recorded
successfully; current pointer update failed.” It MUST NOT roll back, replace,
or erase the authoritative append.

`sera check --require-seal` reads and validates `seals.jsonl`, derives the
current seal from the complete history and current `AssuranceState`, and fails
closed if none is current. It never trusts `seal.json` independently. When a
pointer exists it is validated against the authoritative selection; mismatch
produces `SEAL_POINTER_MISMATCH` and fails validation until the pointer is
regenerated or removed, without changing ledger truth.

Seal v2 remains readable but is `LEGACY_PROVENANCE` for receipt-backed assured
acceptance. It remains a historical `seal.json`, is not converted to v3, and is
not inserted into `seals.jsonl` as though it had been created there. Seal v3
creation requires one current `AssuranceState` and repeats the state/identity
checks immediately before authoritative append.

## 21. CLI evolution

Existing commands remain unless stricter assurance intentionally changes their
result:

```text
sera status
sera next
sera review
sera check
sera seal
```

Additions are:

```text
sera receipt import <receipt.json> --output-file <output> [--task <id>] [--json]
sera task policy --adopt --actor <actor> --reason <reason>
sera review --receipt <execution-id> [--reason <commentary>]
sera check --require-seal
sera explain [--json]
sera report [--format text|markdown|json]
```

Receipt import never invokes a provider. Manual review compatibility remains,
but output explicitly reports its manual/legacy provenance strength.

`sera explain` formats ordered state reasons, cause, bound/current identities,
current stage statuses, required action, forbidden actions, the authoritative
current seal reference, historical seal count, current/stale summary, sealed
HEAD/tree, seal record hash, prior-ledger fingerprint, legacy Seal v2 presence,
and pointer status.

`sera report` includes task, scope, origin, roles, receipts, substitutions,
verification attempts/findings, repository and knowledge bindings, unresolved
findings, current seal, historical seal references and statuses, sealed
HEAD/tree, record hashes, prior-ledger relationships, legacy Seal v2 presence,
pointer status, and final assurance status. Default human output does not dump
full historical seal contents; machine-readable output may include stable seal
references and hashes. Machine provenance fields are read from evidence only.

## 22. Compatibility and migration

Compatibility is read-time and conservative:

- task v1: readable as legacy/pre-existing; no invented policy, knowledge, or
  builder receipt;
- unversioned verification: readable, retains command/result/hash, lacks modern
  environment and repository provenance;
- unversioned review: readable as manual `LEGACY_PROVENANCE`;
- packet v3: readable for diagnostics but cannot satisfy packet v4 receipt
  binding;
- seal v2: readable in its historical `seal.json` location as
  `LEGACY_PROVENANCE`, but cannot satisfy modern strict receipt-backed
  assurance and is never silently converted or copied into `seals.jsonl`.

Default legacy policy may preserve non-assured historical workflows. Assured
tasks reject legacy provenance unless an explicit immutable override snapshot
records actor, reason, scope, and policy decision. No task is silently upgraded.

The 0.5.0 self-hosting task began under task schema v1. After Increment 1 it may
adopt a narrowly scoped bootstrap policy override that permits manual or
controller-observed provenance only for this task. The override allows SERA to
complete its own release workflow without claiming provider attestation. The
final report and seal expose the limitation.

When `seals.jsonl` does not exist, modern history is empty and begins only when
the first real Seal v3 record is created. Migration MUST NOT manufacture a v3
record from a v2 file. A legacy v2 `seal.json` and an optional modern derived
pointer use the same historical pathname but are distinguished by strict schema
readers and task migration state. When that pathname contains a legacy v2 seal,
modern sealing MUST leave it unchanged and omit the optional pointer rather than
replace historical evidence. Current Seal v3 is still derived from
`seals.jsonl`; creating the first v3 history does not rewrite the legacy
artifact merely to simulate prior history.

### 22.1 Migration risks and controls

| Risk | Required behavior |
| --- | --- |
| Config v1 has lanes but no stage policy snapshot | Translate in memory, label the source schema, and require explicit adoption before a strict assured task can gain modern policy semantics. Do not rewrite config during a read. |
| Task v1 lacks origin, repository identity, policy, and knowledge | Normalize as legacy/pre-existing with absent modern bindings; never infer them from current state. |
| Existing assured reviews were accepted from typed reviewer names | Preserve and display them, but block modern strict assured readiness unless a scoped immutable override explicitly permits the bootstrap limitation. |
| Packet v3 has no policy/route/knowledge/model binding | Preserve for audit and require packet-v4 regeneration before receipt-backed execution. |
| Seal v2 omits receipt and policy ledgers | Read the existing `seal.json` as `LEGACY_PROVENANCE` at its historical location; do not rewrite, convert, or copy it into `seals.jsonl`; modern history starts with the first actual Seal v3 creation, and modern assured acceptance requires a fresh v3 record. |
| Mixed legacy and v2 ledger lines | Parse each line through its declared or compatibility schema, retain order, and fingerprint the normalized sequence; malformed lines block rather than disappear. |
| New domain modules replace logic formerly in `core.py` | Characterization tests hold existing non-provenance behavior while new tests prove the domain module is authoritative. Facades delegate rather than duplicate. |
| Configuration changes during an active task | Continue using the bound snapshot and surface the difference; adopt only through an explicit actor/reason event. |

These are intentional compatibility boundaries, not automatic upgrades.

## 23. Security model

### 23.1 Threats and controls

| Threat | Control |
| --- | --- |
| Path traversal or absolute-path escape | Normalize repository-relative paths; reject absolute paths, `..`, and resolved root escape. |
| Symlink attacks | Reject symlink escapes; no-follow final input where supported; verify resolved containment and file identity. |
| Receipt/cache poisoning | Strict bounded schemas, canonical hashes, content-addressed output storage, append-only import audit. |
| Receipt modification | Canonical receipt hash plus ledger fingerprint and downstream seal binding. |
| Output replacement | Content hash comparison on import and before counted use. |
| Stale receipt reuse | Task/repository/HEAD/tree/fingerprint/policy/route/packet bindings and separate currency evaluation. |
| Task ID collision | Existing collision avoidance plus repository/task binding; execution ID conflict poisons the ID. |
| Hash confusion | SHA-256 fields have named domains and strict lowercase encoding; ledger hashing uses domain separators. |
| Untrusted JSON | Size, depth, key-count, type, unknown-field, Unicode-control, and finite-number checks. |
| Shell/provider command injection | Receipt data never becomes a command; native dispatch absent. |
| Prompt injection in repository files | Typed attribution distinguishes repository content, claim, instruction, invariant, and machine evidence. Repository text cannot change controller policy. |
| Secret leakage | Credential-bearing remotes stripped; raw output excluded; receipt metadata bounded; secret-risk packet findings block dispatch rather than silently redact evidence. |
| TOCTOU | Task lock plus before/after identity checks at all state transitions. |
| Concurrent duplicate imports | Locked uniqueness/conflict evaluation and atomic append. |
| Seal pointer tampering or pointer/ledger disagreement | Treat `seal.json` as derived only; validate it against the current record selected from `seals.jsonl`, report `SEAL_POINTER_MISMATCH`, and never let it override ledger truth. |
| Seal history deletion, mutation, or reordering | Order-sensitive ledger and prefix fingerprints make changed history observable when compared; malformed relationships fail closed and no reader normalizes a record away. |
| Duplicate or conflicting seal records | Preserve exact duplicates, surface `SEAL_RECORD_DUPLICATE`, and block strict acceptance until explicitly explained; the same `seal_id` with different content is `SEAL_RECORD_CONFLICT` and fails closed. |
| Truncated or partial seal append | Append under the task lock; malformed or incomplete lines, including the final line, block modern assurance and are never silently ignored. |
| Seal replay between tasks or repositories | Bind task fingerprint and logical repository identity in each record and validate them before historical validity or current eligibility can count. |

Local SHA-256 and prefix fingerprints detect inconsistency relative to available
state; they are integrity mechanisms, not remote attestation and do not prevent
a malicious local actor from coherently rewriting the entire repository and
task history. No new runtime dependency is required.

## 25. Test strategy

Every behavior change follows red-green-refactor. Test classes include:

- schema unit tests for strictness, bounds, canonicalization, and legacy reads;
- receipt unit tests for all bindings, identity strength, substitution, replay,
  conflicts, and output hashes;
- state-machine tests for every status/reason transition;
- integration tests for CLI import/review/next/check/seal flows;
- migration tests proving old evidence remains readable but not strengthened;
- seal-history preservation tests that create seal A and seal B and prove both
  remain in authoritative ledger order;
- current-selection tests that retain A as historically valid but stale after
  HEAD B is fully assured and select B as current;
- pointer deletion tests proving history and current selection derive from
  `seals.jsonl` without `seal.json`;
- pointer tampering tests proving a stale or fake pointer reports
  `SEAL_POINTER_MISMATCH` and cannot override history;
- historical record mutation tests proving fingerprint or prefix validation
  changes and assurance fails closed;
- historical record deletion tests proving the ledger fingerprint changes and
  bound prefix/pointer comparisons fail where available;
- historical record reorder tests proving the ledger fingerprint changes and
  prefix validation fails closed;
- exact-duplicate tests proving both entries remain observable, the ledger
  fingerprint changes, and strict acceptance blocks deterministically;
- conflicting-identity tests proving one `seal_id` with different content fails
  closed;
- legacy-v2 tests proving historical `seal.json` reads as
  `LEGACY_PROVENANCE` and is not silently converted to Seal v3;
- post-seal evidence-movement tests proving an appended verification attempt
  makes the earlier seal stale without mutating it;
- failed-pointer-write tests proving a completed `seals.jsonl` append survives
  with every previous seal unchanged and a recoverable pointer error;
- seal TOCTOU tests that mutate bound evidence after derivation but before
  append and prove no candidate record is appended;
- malformed/truncated-final-record tests proving partial append is never
  ignored;
- adversarial filesystem and hostile JSON tests;
- deterministic packet/context/knowledge tests;
- TOCTOU tests using controlled identity mutation hooks;
- end-to-end self-hosting-shaped assured tasks;
- full existing regression suite on Python 3.11-compatible code.

Existing tests change only where an intentional stronger invariant invalidates
the old expectation. Each such test documents the former behavior, the new
invariant, and why legacy assertion-based evidence no longer suffices.

## 28. Resolved and deferred decisions

All implementation-blocking design decisions are resolved by this specification.

Deliberately deferred beyond 0.5.0:

- native provider invocation and provider-specific adapters;
- cryptographic receipt signing or provider attestation protocols;
- remote transparency logs or database storage;
- automatic policy adoption for active tasks;
- proof of human/model non-collusion beyond observable receipt dimensions.

These deferrals do not weaken the 0.5.0 invariant: absence of evidence remains a
blocked or explicitly limited state, never inferred assurance.
