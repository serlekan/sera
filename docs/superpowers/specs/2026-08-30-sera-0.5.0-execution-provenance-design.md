# SERA 0.5.0 Execution Provenance and Governed Dispatch Design

**Status:** Design approved; specification under independent review; implementation not started
**Date:** 2026-08-30
**Release:** SERA 0.5.0
**Self-hosting task:** `20260830T034346Z-sera-0-5-0-execution-provenance`

## 1. Purpose

SERA 0.5.0 closes the gap between a declared route and the evidence that a
specific execution actually occurred. The release binds task policy, repository
identity, packet input, execution-target identity and evidence strength, observed
execution identity, output, verdict, review, verification, and seal without
introducing native provider invocation.

The governing rule is:

> SERA must never claim stronger assurance than the evidence it actually possesses.

The normative execution-evidence corollary is:

> Execution evidence MUST NOT establish its own trust level.

A source identifier, source class, attestation claim, enforcement claim,
evidence hash, or execution-binding hash supplied by external input does not
become trusted merely because it appears in structurally valid JSON. Strong
execution evidence requires all five of:

```text
immutable registered source identity
+ source capability ceiling
+ policy authorization
+ trusted verification result
+ execution/target binding
```

The architectural dependency is fixed:

```text
provenance foundation -> evidence integrity -> reporting and release
```

The work is delivered as three independently reviewable increments. Each
increment leaves the repository valid and testable. A later commit makes an
earlier increment review historical; no increment review substitutes for the
fresh final release review and gate.

## 3. Scope and non-goals

### 3.1 In scope

- versioned execution receipts and import records;
- canonical execution roles and implementation origin;
- immutable policy and route snapshots;
- provider/model substitution governance;
- trusted, append-only manual substitution decisions;
- explicit legacy Task v1 to Task v2 contract adoption;
- receipt validity, currency, uniqueness, and replay protection;
- versioned trusted execution targets and execution-state evidence;
- immutable execution-evidence source registration and capability ceilings;
- canonical machine-verified execution-to-target bindings;
- one authoritative derived `AssuranceState`;
- versioned verification history;
- structural reviewer packets and lint evidence;
- deterministic context reduction and overflow manifests;
- repository knowledge fingerprints;
- `sera explain` and `sera report`;
- conservative compatibility and migration;
- seal v3 and exact-state self-hosted release evidence.

### 3.2 Not in scope

- direct OpenAI, Anthropic, Gemini, or other provider invocation;
- provider-specific SDK dependencies in the core package;
- a database or generic event-store rewrite;
- cryptographic claims that an external provider or person performed work when
  SERA only possesses a local assertion;
- mandatory code signing, remote attestation, or provider-specific evidence
  protocols as a condition of 0.5.0 operation;
- claims of continuous execution-window immutability when SERA possesses only
  equal pre/post repository checkpoints;
- automatic rewriting, deletion, or strengthening of historical evidence;
- automatic silent policy adoption after configuration changes;
- automatic promotion of legacy task or substitution assertions into modern
  assurance evidence;
- repair of the seven unrelated baseline lint errors.

## 4. Architecture

### 4.1 Domain modules

New assurance semantics live in focused modules. `core.py`, `controller.py`, and
`cli.py` remain compatibility and orchestration facades; they are not hidden
sources of truth for new readiness rules.

| Module | Responsibility |
| --- | --- |
| `schemas.py` | Schema constants, bounded strict JSON readers, canonical serialization, ledger fingerprints, compatibility classification. |
| `provenance.py` | Canonical roles, implementation origin, repository identity, policy/route snapshots, trusted substitution decisions, evidence-source registrations, trusted execution targets, verified execution bindings/evidence, task-contract adoption, receipt import and validation, independence checks. |
| `verification.py` | Verification attempt v2 capture, append-only storage, environment/dependency identity, derived history findings. |
| `knowledge.py` | Contained knowledge-source discovery, symlink/root escape prevention, immutable hashes. |
| `packets.py` | Typed packet model, packet v4 bindings, lint records, deterministic reduction and overflow manifests, rendering. |
| `assurance.py` | Authoritative active-contract interpretation, substitution-decision eligibility, derived `AssuranceState`, sequencing, seal eligibility, reason codes. |
| `reporting.py` | Text, Markdown, and JSON transformations of state and evidence; no readiness decisions. |

Dependencies flow toward domain modules. `assurance.py` consumes normalized
records from the other domain modules. `reporting.py` consumes
`AssuranceState`; it never imports controller readiness helpers. Domain modules
must not import `cli.py` or `controller.py`.

### 4.2 External execution boundary

```text
typed packet
  -> select policy-authorized evidence-source registration
  -> trusted execution-target creation/authorization
  -> registered enforcement/observation boundary
  -> machine-verified execution-to-target binding
  -> external provider-neutral runner, controller, or future adapter
  -> raw output plus ExecutionReceipt v1
  -> canonical trusted execution-state evidence
  -> hostile-input-safe receipt import
  -> intrinsic and binding validation
  -> currency evaluation
  -> stage evidence
  -> AssuranceState
```

A future native adapter must use this same source-registration, target, binding,
evidence, receipt, import, and validation boundary. It does not receive a
privileged path and cannot weaken provenance semantics.
Checkpoint observation, target enforcement, and execution-window attestation are
distinct evidence strengths throughout this boundary.

## 5. Canonical serialization and immutable ledgers

All new persisted records contain an integer `schema_version`. Strict readers
reject missing, Boolean, non-integer, negative, and unsupported versions.

Canonical JSON is UTF-8 JSON with:

```text
sorted object keys
no insignificant whitespace
Unicode preserved rather than ASCII escaped
finite JSON values only
arrays preserved in declared order
```

Ledger fingerprints are semantic and order-sensitive:

1. Strictly parse every non-empty line. A malformed line blocks assurance; it
   is never skipped.
2. Normalize the record through its schema or explicit compatibility reader.
3. Canonically serialize each normalized record.
4. Hash each record with SHA-256.
5. Hash a domain separator, schema family, record count, and the ordered
   sequence of `index`, NUL separator, and record hash.

This makes ordering, duplicate records, appended records, and field mutations
observable while making platform newline style and insignificant JSON spacing
irrelevant. Ledger writes are append-only. No API updates or removes a record.
This rule applies to every assurance ledger, including Seal v3 history. Ordinary
operation MUST NOT rewrite, replace, delete, or omit a previously persisted
record merely because newer or cleaner evidence exists. A malformed or
incomplete final JSONL record blocks modern assurance and is not silently
ignored.

Task-scoped mutating operations use a cross-platform atomic lock directory under
the task runtime directory. Lock acquisition failure is closed. SERA does not
silently remove a lock it cannot prove is stale. A record is serialized and
written as one UTF-8 append while the lock is held.

The repository-level evidence-source registry uses an equivalent repository
registry lock. Registry append and task mutation locks are never acquired in
opposite order: a task operation resolves and validates an already-persisted
registration before taking the task lock, then re-reads that exact registration
hash under the task lock before appending task evidence. It never creates or
changes a source registration as a side effect of receipt or evidence import.

distinguished by its schema rather than treated as a ledger entry.

task, but a legacy v1 `task.json` remains untouched at its historical location

## 7. Task v2, repository identity, and knowledge identity

### 7.1 Task v2 additions

Task v2 retains existing fields and adds:

```text
implementation_origin: sera_builder | external | pre_existing
repository_identity: RepositoryIdentityV1
active_policy_hash: sha256
knowledge_sources: ordered KnowledgeSourceV1[]
knowledge_fingerprint: sha256
knowledge_assessment_state: unassessed_by_pre_increment_2_runtime | assessed
provenance_class: modern | legacy
```

New implementation tasks default to `sera_builder`. Importing or validating
already-existing work requires an explicit `external` or `pre_existing` origin.
Compatibility reads of task v1 use `pre_existing` and `legacy` internally; they
do not claim a routed builder authored historical changes. A compatibility read
MUST NOT persist those normalized defaults or make the task modern. A legacy
task remains `TASK_CONTRACT_LEGACY` until an explicit contract adoption
succeeds; strict assured readiness also reports
`TASK_CONTRACT_ADOPTION_REQUIRED`.

Increment 1 creates task v2 before knowledge discovery is implemented. During
that increment, `knowledge_sources` is an empty ordered list and its fingerprint
is the canonical empty-collection fingerprint, explicitly reported as
`unassessed_by_pre_increment_2_runtime`. Increment 2 begins populating the same
v2 fields for newly created or explicitly re-contracted tasks without another
task schema change. Existing Increment 1 contracts retain their historical
empty, unassessed snapshot. Knowledge discovery that changes the contract
requires another explicit task-contract adoption; a policy-only adoption MUST
NOT mutate it. An empty list never implies that a repository has no governing
knowledge. `assessed` with an empty list is a distinct explicit result and has
a different contract identity from the pre-Increment-2 unassessed state.

### 7.2 RepositoryIdentityV1

HEAD and tree do not distinguish all logical repositories. Task and receipt
bindings therefore include a logical repository identity snapshot:

```text
schema_version: 1
strategy: configured | git_remote_root | local_git_dir
logical_id: sha256
strength: configured | derived | local_only
components: bounded non-secret diagnostic hashes/identifiers
```

Resolution order:

1. `configured`: an explicit non-secret repository ID in config v2. `sera init`
   generates it once. It may be committed as policy.
2. `git_remote_root`: SHA-256 of canonical, credential-stripped sorted remote
   identities plus the immutable root commit.
3. `local_git_dir`: SHA-256 of the resolved Git common-directory identity and
   root commit, reported as `local_only`.

Remote canonicalization removes usernames, passwords, query strings, and
fragments before hashing. Raw credential-bearing URLs are never persisted.

This identity proves only that SERA compared the same recorded logical
identifier and components. It is not a signature, ownership proof, or defense
against a malicious actor who copies the repository ID and all task state.
Reports expose its strategy and strength.

### 7.3 KnowledgeSourceV1

Each source records:

```text
schema_version: 1
path: normalized repository-relative path
sha256: content hash
bytes: non-negative integer
source_class: repository | workspace | product
```

Discovery accepts only configured relative paths. It rejects absolute paths,
empty paths, `..` traversal, resolved paths outside the repository, symlink
escapes, non-regular files, unreadable files, and files over the configured
limit. Paths are sorted by normalized path before fingerprinting. The knowledge
fingerprint is part of task contract identity. Legacy tasks receive no
retroactive knowledge entries.

### 7.4 Authoritative task-contract history

`task-contracts.jsonl` is the authoritative append-only history for modern task
contracts. It follows Section 5 and accepts two explicitly discriminated record
forms:

- a `TaskContractV2` line for a task created natively under the modern
  contract; or
- a `TaskContractAdoptionV1` line that embeds the complete new
  `TaskContractV2` when adopting or re-contracting an existing task.

`TaskContractV2` contains:

```text
schema_version: 2
record_type: task_contract
task_id
objective and bounded task metadata
owned scope and constraints
verification requirements
repository_identity
implementation_origin
active_policy_hash
knowledge_sources
knowledge_fingerprint
knowledge_assessment_state
provenance_class
bootstrap_boundary, optional
contract_hash
```

Its stable identity is:

```text
contract_hash = SHA256(canonical TaskContractV2 excluding contract_hash)
```

No other field is excluded. The active modern `task_contract_fingerprint` is
this `contract_hash`. The existing state-sensitive `task_fingerprint` remains a
separate identity over the active contract plus its defined evidence and change
state; its modern derivation MUST incorporate `task_contract_fingerprint`.
Every modern packet, receipt, review, gate, verification attempt, and Seal v3
binds the active task-contract fingerprint and also binds the dynamic task
fingerprint wherever that artifact already requires current-state freshness.
Both values MUST change across v1 adoption; equivalence is not inferred merely
because objective or scope text is unchanged.

The 0.5.0 dynamic `task_fingerprint` covers the active contract fingerprint and
the defined repository/change inputs, but excludes append-only assurance-ledger
bytes. Those collections have separate order-sensitive fingerprints in
`AssuranceState` and Seal v3. This prevents a decision, receipt, verification,
or review from making its own task binding stale merely by being appended while
still ensuring later evidence movement changes readiness and seal currency.

For a legacy transition, `TaskContractAdoptionV1` contains:

```text
schema_version: 1
record_type: task_contract_adoption
adoption_id
task_id
previous_contract_schema: 1 | 2
previous_contract_hash
previous_task_contract_fingerprint
new_contract_schema: 2
new_contract: complete TaskContractV2
new_contract_hash
new_task_contract_fingerprint
repository_identity
head_sha
tree_sha
implementation_origin
policy_snapshot_hash
knowledge_assessment_state
knowledge_sources
knowledge_fingerprint
actor
reason
adopted_at
bootstrap_limitations
policy_result: permitted
adoption_hash
```

The first legacy `previous_contract_hash` is the domain-separated SHA-256 of
the canonical strict compatibility normalization of the complete Task v1
record, including its source schema. `previous_task_contract_fingerprint`
retains the legacy contract fingerprint used by v1 evidence.
`new_contract_hash` MUST equal the embedded contract's validated
`contract_hash`, and `new_task_contract_fingerprint` MUST equal that new hash.
The top-level repository, origin, policy, knowledge, and bootstrap fields are
bounded transition summaries and MUST exactly equal their counterparts in the
embedded new contract; any disagreement makes the adoption invalid.
For later re-contracts, the previous hash and fingerprint must identify the
currently active v2 contract. The adoption identity is:

```text
adoption_hash = SHA256(canonical TaskContractAdoptionV1 excluding adoption_hash)
```

No other field is excluded. `adoption_id` is a lowercase UUIDv4 generated under
the task mutation lock. It identifies an adoption event and is not proof of who
the actor is. Actor identity remains only as strong as the configured local
authentication or observation boundary and is reported accordingly.

Embedding the complete new contract makes the old-contract to adoption to
new-contract relationship one canonical append. A reader parses and validates
the complete ledger, all hashes, repository bindings, and the chain from each
record's previous contract to the next. The newest valid chained contract is
active; the last physical line is not trusted without validation. Missing or
invalid modern history cannot be repaired by `task.json`.

A natively created Task v2 appends its complete `TaskContractV2` as the first
authoritative ledger line under the task mutation lock before emitting any
derived projection or packet. Creation failure leaves no partially modern task;
a malformed or truncated first line is invalid under Section 5.

`task.json` is optional derived compatibility state for a modern task and is
never independently authoritative after `task-contracts.jsonl` exists. For a
migrated task whose historical `task.json` is v1, SERA MUST leave that file
unchanged and omit the modern projection. Deleting or changing a derived v2
projection does not change authoritative history; mismatch fails validation or
is regenerated from the ledger. Pointer/projection failure after a successful
ledger append cannot roll back the authoritative adoption.

### 7.5 Explicit adoption, conflict, and TOCTOU behavior

`sera task contract --adopt` is the only transition from a compatibility-read
Task v1 to a modern Task v2 contract. A policy-only command cannot perform this
transition. Under the task mutation lock, adoption MUST:

1. read the legacy or current active contract and compute its contract hash;
2. capture repository identity, HEAD, and tree;
3. resolve and, if required, append the immutable policy snapshot;
4. require explicit implementation origin, actor, reason, policy result, and
   structured bootstrap limitations;
5. construct the complete new Task v2 contract and adoption record;
6. re-read the active contract, repository identity, HEAD/tree, and policy;
7. fail without appending if any captured value changed;
8. append exactly one adoption record containing the new contract; and
9. only after authoritative append, optionally update a non-authoritative v2
   `task.json` projection when no historical v1 file occupies that path.

An exact duplicate adoption remains observable, changes the ledger fingerprint,
produces `TASK_CONTRACT_ADOPTION_DUPLICATE`, and blocks strict assured
acceptance until explained through immutable policy.
The same `adoption_id` with different content is
`TASK_CONTRACT_ADOPTION_CONFLICT` and fails closed. An adoption based on a stale
previous contract, another repository identity, or moved HEAD/tree is rejected.
Silent auto-adoption is forbidden.

Malformed adoption or embedded-contract evidence reports
`TASK_CONTRACT_ADOPTION_INVALID`; a no-longer-active previous contract or
HEAD/tree movement reports `TASK_CONTRACT_ADOPTION_STALE`; contract/fingerprint
disagreement reports `TASK_CONTRACT_FINGERPRINT_MISMATCH`; and repository
disagreement reports `TASK_CONTRACT_REPOSITORY_MISMATCH`.

A v1 adoption MUST use `pre_existing` or `external` unless independently valid
historical builder evidence already satisfies the modern policy; compatibility
normalization or bootstrap assertions never suffice. A later prospective
re-contract may select `sera_builder` only for a newly bounded implementation
scope with current builder evidence and an explicit boundary; it cannot
reclassify earlier work.

For the pre-Increment-2 self-hosting adoption, the embedded contract records:

```text
implementation_origin: pre_existing
knowledge_sources: []
knowledge_fingerprint: canonical empty-collection fingerprint
knowledge_assessment_state: unassessed_by_pre_increment_2_runtime
provenance_class: modern
bootstrap_limitations: explicit legacy boundary and modern stages still required
```

This does not assert that the repository has no governing knowledge and does
not make historical work modern builder output. When Increment 2 discovers
knowledge, the operator performs another explicit contract adoption that binds
the discovered sources and produces a different active task fingerprint. No
reader or policy-only command silently mutates the Increment 1 contract.

## 8. Immutable policy and route snapshots

### 8.1 Configuration v2

Config v2 adds provider-neutral stage policies for the four canonical roles,
provenance, execution-state evidence, and candidate source-acceptance
requirements, legacy behavior,
repository identity, knowledge
sources, context limits, and substitution rules. Config v1 lanes are accepted
through a compatibility translator. Compatibility aliases terminate there.

### 8.2 PolicySnapshotV1

A task policy snapshot contains only normalized policy relevant to that task:

```text
schema_version
task_id
captured_at
trigger: task_created | ownership_confirmed | explicit_policy_adoption | task_contract_adoption
mode and risk
required stages
implementation-origin rules
provenance-strength requirements
execution-state policy by stage:
  minimum_evidence_class
  accepted_source_registration_hashes, preferred for strict self-hosting
  accepted_source_types, optional bounded alternative
  required_capabilities
  accepted_verification_methods
legacy override, if any
substitution rules
independence requirements
verification requirements
context budgets
knowledge policy
repository identity requirement
snapshot_hash
```

The hash excludes only its own `snapshot_hash` field. The task references the
active snapshot hash. Current configuration is not used to reinterpret a
historical execution.

`PolicySnapshotV1` is the sole authority for source authorization. Exact
registration hashes are required for strict self-hosting stages unless an
explicitly bounded source-type/capability/method rule is necessary and records
the same limitation. A source must satisfy every configured constraint; a
claimed class never satisfies one. A policy snapshot cannot authorize a source
above its registered ceiling or for an unsupported stage, target kind, or
verification method.

Ownership confirmation appends a new policy snapshot because it may alter risk
and routing. Other configuration changes do not alter an active task. Explicit
policy adoption uses a task policy command requiring actor and reason and
appends a candidate snapshot; it does not rewrite old snapshots. For a modern
task, that candidate becomes active only when an explicit task-contract adoption
binds its hash. The contract adoption then invalidates packets and downstream
current evidence through the new contract and policy fingerprints. For a legacy
task, the candidate may be bound by its first contract adoption. Policy
adoption alone never silently promotes Task v1, changes the active Task v2
contract, or rewrites task identity.

### 8.3 RouteSnapshotV1

Every packet binds a route snapshot containing:

```text
schema_version
task_id
canonical stage
policy_hash
primary requested provider/model
ordered approved fallbacks
required identity-evidence class
required execution-state evidence class
required output/verdict fields
snapshot_hash
```

Receipts bind both policy and route hashes. Source authorization is not
duplicated in the route: the route binds the authoritative policy and the
required class, while the selected registration is bound later by the target,
execution binding, evidence, and receipt. Changing current configuration cannot
retroactively approve a substitution or evidence source. The implementation
therefore never has to choose between conflicting route and policy source rules.

## 9. Canonical roles and implementation origin

Internal roles are exactly:

```text
implementation_builder
implementation_validator
independent_reviewer
release_gate
```

`builder`, `independent`, and `gate` are input aliases only. Persisted modern
records and domain functions use canonical roles.

Origin semantics:

- `sera_builder`: policy requires a current valid builder receipt whenever the
  task claims modern builder provenance. That receipt binds both the governed
  input state and the implementation state the builder produced. Under strict
  modern assured policy, its governed input execution must also have
  policy-accepted `EXECUTION_STATE_ENFORCED` or appropriately strong
  `EXECUTION_STATE_ATTESTED` evidence. The evidence proves that the builder
  consumed governed input A; it does not prove output B.
- `external`: policy may require a validator receipt but must report that SERA
  cannot prove who authored the implementation.
- `pre_existing`: policy may require validation of existing work and reports no
  builder-origin claim.

An `implementation_validator` receipt never satisfies an
`implementation_builder` requirement. Distinct role labels alone do not prove
distinct actors.

The strict modern defaults are:

```text
implementation_builder, when implementation_origin = sera_builder:
  governed input requires ENFORCED or accepted ATTESTED evidence
implementation_validator:
  requires ENFORCED or accepted ATTESTED evidence
independent_reviewer:
  requires ENFORCED or accepted ATTESTED evidence
release_gate:
  requires ENFORCED or accepted ATTESTED evidence
```

Policy may weaken a stage only for an explicitly limited, non-strong assurance
profile. That result MUST NOT be reported as the strongest strict provenance
level. The builder legitimately changes A to B: execution-state evidence binds
its input A, while Section 10.1 independently establishes exact committed output
B and current builder currency.

## 10. ExecutionReceiptV1

### 10.1 Repository-state model

`ExecutionRepositoryStateV1` is the shared nested state object used by packet,
receipt, import-observation, assurance, and seal evidence:

```text
schema_version: 1
repository_identity
head_sha
tree_sha
task_contract_fingerprint
task_fingerprint
state_kind: committed | working_tree
review_change_fingerprint, optional except where stage or policy requires it
```

`state_kind: committed` names an exact Git commit and its tree.
`state_kind: working_tree` additionally requires
`review_change_fingerprint`, computed by the existing authoritative review
change/coverage algorithm over the committed, staged, unstaged, and relevant
untracked task delta. It does not make an uncommitted state equivalent to a
commit.

Every receipt has an `input_state`. It MUST equal the Packet v4 Core Binding
state and the repository/task state authorized by the route and policy. An
`implementation_builder` receipt additionally has a required `output_state`.
Receipts for `implementation_validator`, `independent_reviewer`, and
`release_gate` are non-mutating and `output_state` MUST be absent. SERA records
independently observed pre/post checkpoints for those stages. Equal checkpoints
establish only that no difference was observed at those instants; they do not
prove that the repository remained unchanged throughout external execution or
that the stage consumed only that checkout state.

For strict assured builder provenance, `output_state.state_kind` MUST be
`committed`, bind exact output HEAD/tree and active contract/dynamic task
fingerprints, and bind a review-change fingerprint covering the complete task
delta. No builder-attributable staged, unstaged, or relevant untracked task
change may remain outside that committed output. Unrelated pre-existing
baseline dirt remains separately identified and does not become builder output.

A policy may explicitly permit a `working_tree` builder result only for a
non-strict, non-assured workflow. It must bind the complete current review
change fingerprint and is reported as limited provenance; it can never satisfy
a strict modern builder requirement. These are the normative state cases:

```text
A. committed A -> builder -> committed B: strict-capable when claim and observation match B
B. committed A -> builder -> working tree A+delta: non-strict only when policy explicitly permits
C. committed A -> non-mutating stage -> A: checkpoint-valid when both observed checkpoints equal A
D. committed A -> non-mutating stage -> B or A+delta: invalid for the stage
```

Case C means checkpoint-valid, not automatically strict exact-state eligible.
Execution-window strength is evaluated separately under Section 10.2.

Builder currency means the current implementation state exactly equals the
validated `output_state`. Later repository movement to C makes the builder
receipt stale. Appending excluded assurance ledgers does not itself stale the
receipt because the dynamic task fingerprint excludes those ledgers under
Section 7.4.

An isolated worktree can satisfy strict builder provenance only when its exact
output commit, tree, task change identity, and active contract identity are
integrated into and independently observed in the governed repository. Path
identity is irrelevant; Git and task identity are authoritative. A cherry-pick
that creates a different commit is a different output state. A patch-only
handoff is external/manual evidence until it is integrated, validated, and
observed; it cannot itself satisfy a strict modern builder receipt.

### 10.2 Trusted execution target and execution-state evidence

The normative execution-state evidence classes are:

```text
CHECKPOINT_OBSERVED
EXECUTION_STATE_ENFORCED
EXECUTION_STATE_ATTESTED
```

`CHECKPOINT_OBSERVED` means SERA independently observed the expected state at
defined controller checkpoints, normally immediately before authorization and
after external execution. Equality means only “no repository difference was
observed at the recorded checkpoints.” It MUST NOT be described as continuous
immutability, proof that the stage read only A, or proof that transient A -> B ->
A movement did not occur. It is retained as limited evidence and policy may
allow it for non-strict or historical workflows.

`EXECUTION_STATE_ENFORCED` means the stage was structurally constrained to
consume an immutable or content-addressed target exactly representing Packet v4
input state A, and trusted binding evidence demonstrates that the external stage
was directed to and operated against that target. The target may be a read-only
isolated Git worktree, immutable Git object/snapshot, content-addressed root, or
runner sandbox populated from the exact bound state. No operating-system-specific
mechanism is mandated, but target drift MUST change identity or invalidate the
evidence.

`EXECUTION_STATE_ATTESTED` means a policy-approved registered verifier
established the declared execution-state property across the external execution
boundary to the documented strength of that source. It is not a universal
cryptographic attestation claim. A local adapter can remain vulnerable to a
local actor controlling both adapter and repository. SERA reports that
limitation and does not infer remote attestation, provider identity, or
non-collusion.

#### 10.2.1 ExecutionEvidenceSourceV1 trust root

Authoritative source registrations are `ExecutionEvidenceSourceV1` records in
the repository-level append-only registry
`.sera/execution-evidence-sources.jsonl`:

```text
schema_version: 1
source_id
source_type: controller | registered_adapter | registered_observer |
             provider_verifier
display_name, optional bounded diagnostic field
implementation_identity
implementation_version
capability_ceiling: CHECKPOINT_OBSERVED | EXECUTION_STATE_ENFORCED |
                    EXECUTION_STATE_ATTESTED
supported_stages: normalized non-empty subset of the four canonical roles
supported_target_kinds: normalized non-empty subset of ExecutionTargetV1 kinds
verification_method: provider-neutral method name and method version
registration_origin: sera_builtin | sera_admin_operation |
                     normalized_static_configuration
registered_by
registered_at
registration_scope
registration_hash
```

Set-valued fields are duplicate-free and normalized into schema-defined order
before hashing. `implementation_identity` and `registration_scope` are strict,
bounded provider-neutral objects; unknown fields are rejected. Scope states
whether a source may be considered for one logical repository, a bounded set of
repositories, or another explicitly represented administrative domain. Global
reuse is permitted only when both registration scope and task policy permit it.

`source_id` is an identifier only. It proves none of adapter authenticity,
provider identity, execution authenticity, trustworthiness, or non-collusion.
The source's possible assurance strength comes from the immutable verifier
boundary, its registered capability and scope, the trusted machine result, and
task-bound policy acceptance. Names such as `trusted-runner` or claimed classes
such as `registered_adapter_enforced` are just external text unless resolved to
an authoritative registration and verified through its registered method.

The registration identity is exactly:

```text
registration_hash =
SHA256(canonical ExecutionEvidenceSourceV1 excluding registration_hash)
```

No other field is excluded. An exact repeated canonical record with the same
`source_id` is retained and reported with deterministic diagnostic
`exact_duplicate_registration`; it does not create a new semantic identity.
The same `source_id` with different canonical content produces
`EXECUTION_EVIDENCE_SOURCE_CONFLICT` and fails strict use of that source closed.
An unsupported schema is invalid, an unknown hash is unusable, and a referenced
hash must identify the exact record whose `source_id` is used.

A registration record is never updated in place. Any change to implementation
identity or version, capability ceiling, supported stages, supported target
kinds, verification method or version, configuration fingerprint, or scope
requires a new registration with a new `source_id` and `registration_hash`.
Materially changed verifier logic therefore has a new registration identity.
Historical evidence is evaluated using the source registration and policy
snapshot that governed it when it was created; it is never silently re-run
through newer verifier logic. Re-evaluation may append a new derived observation
but cannot rewrite or reclassify the historical record.

Registration occurs only through a SERA-controlled administrative/domain
operation, conceptually:

```text
sera evidence-source register ...
```

The operation validates the implementation or observer configuration,
determines source type, capability ceiling, supported stages and target kinds,
binds implementation identity/version and verification method/version, records
actor and time, re-reads its administrative scope under the repository registry
lock, appends one canonical registration, and returns `source_id` and
`registration_hash`. Arbitrary prebuilt registration JSON cannot be imported and
trusted. Statically configured sources use the same normalization and trusted
operation; their exact registration must exist before task policy can select
them.

For in-process/core observers, reproducible implementation identity includes
SERA version, module identity, registered implementation name, and normalized
configuration fingerprint. For external adapters it includes adapter identifier
and version, executable or package identity hash where available, and normalized
configuration fingerprint. Absence of an executable/package hash is an explicit
limitation and may make the source ineligible under strict policy. This local
identity is not remote attestation.

SERA ships a deterministic built-in controller checkpoint registration whose
manifest supplies stable registration metadata and whose ceiling is exactly
`CHECKPOINT_OBSERVED`. It requires no user registration merely to preserve
controller checkpoint evidence. It cannot manufacture enforced or attested
evidence. Its canonical record or immutable built-in registration snapshot is
resolved exactly like any other source for validation and sealing.

The registry is repository-level so a valid registration may be reused, but
task assurance binds only the exact selected registration records/hashes. It
does not bind the complete global registry fingerprint. Consequently, appending
an unrelated registration does not stale or strengthen a task. A later policy
that stops accepting registration A is the 0.5.0 disablement model; no mutable
deletion or global-config removal silently revokes historical evidence. An
active task changes accepted registrations only through explicit policy adoption
and, where Sections 7 and 8 require it, task-contract adoption.

#### 10.2.2 Capability, verification, and policy derivation

Capability order is:

```text
CHECKPOINT_OBSERVED < EXECUTION_STATE_ENFORCED < EXECUTION_STATE_ATTESTED
```

A source can never produce evidence above its registered ceiling, even when an
external payload claims a stronger source or evidence class. An enforced source
does not become attested without an attestation-capable registration. The
effective class is derived, never accepted from an evidence payload:

```text
claimed evidence class (diagnostic only)
  intersect registered capability ceiling
  intersect trusted binding-verification result and method strength
  intersect source stage/target/scope support
  intersect task-bound policy authorization
  -> effective evidence class and policy eligibility
```

A missing/invalid/conflicting source, insufficient ceiling, unsupported stage or
target, unaccepted method, or policy rejection prevents strong evidence from
counting. Policy may require different registration hashes for builder and
reviewer execution, but source separation is not universal proof of independence.
Observer independence from a provider is claimed only when policy and observable
metadata establish the required separation.


No other field is excluded. An opaque or externally supplied SHA-256 value does

binding and does not erase the earlier result.

Binding methods classify proof mechanisms but are not proof by their names. The
selected registration must authorize the method and target kind. The trusted

```text

    source_registration,
    target,
    packet,
    execution_id,

```

The result contains status, exact source registration hash, binding method,
execution and target identities, optional evidence artifact hash, and bounded

external input cannot select or replace it. The verifier result enters through
the trusted internal domain boundary, is re-bound to task/repository/contract/
policy/route/packet state, and becomes `ExecutionBindingV1`. Receipt import
cannot register a source, change capability, select an accepted verifier, create
a source registration, manufacture a binding, or upgrade an evidence class.

External adapter evidence follows exactly:

```text
external evidence payload
  -> registered verifier chosen from immutable source registration
  -> bounded parsing
  -> machine verification
  -> canonical ExecutionBindingV1
  -> canonical ExecutionStateEvidenceV1
```

Unverified input remains received, failed, indeterminate, or manual evidence and
cannot count as strong assurance.

#### 10.2.4 Increment 1 registered external runner

Increment 1 implements `SERA Registered External Runner V1`, a provider-neutral
enforcement source with ceiling `EXECUTION_STATE_ENFORCED`. It does not call a
provider SDK or interpret provider-specific output. Its registered
implementation/configuration identity includes the runner wrapper version,
command-template fingerprint, target-handling backend, isolation properties, and
verification-method version.

For one SERA-generated execution ID E, the trusted runner operation selects a
policy-authorized registration R, materializes and verifies exact target T(A/P),
invokes a pre-registered argv-form external command without shell interpolation
using T as the controlled working-directory/target handle, records the exact
process-launch-to-target association and completion, revalidates target identity,
and emits a machine-verifiable binding result. The backend must structurally
direct repository-relative source access to T and prevent the mutable governed
checkout from being substituted as the runner workspace. Merely naming a target,
setting an unverifiable text field, or observing equal checkpoints is
insufficient. If the available backend can prove only working-directory intent
and not the registered enforcement property, the result is `INDETERMINATE` and
cannot exceed `CHECKPOINT_OBSERVED`.

The runner establishes only that the registered boundary launched/directed E
against T to its documented local enforcement strength. It does not prove which
remote provider reasoned, that the process read no external non-repository data,
or that a malicious local administrator did not control both runner and
repository. Those limitations are reported. This generic execution-target
enforcement/runner observation is part of Increment 1 because its review consumes
the proof. Native provider dispatch remains deferred: governing where and how a
generic command consumes repository state does not make SERA a provider client.
Future native dispatch uses this same registration, target, binding, evidence,
receipt, and validation chain without privilege.

`evidence_hash` is SHA-256 over the canonical record excluding only

Validation requires the registration to exist, match its hash and source ID,
support the stage and target kind, remain within scope and capability ceiling,
be accepted by the governing policy snapshot, authorize the binding method, and
have produced a trusted matching binding result. All task, repository, contract,
dynamic fingerprint, policy, route, packet, execution, target, and expected-state
bindings must agree. A registration is reusable only as a trust root;
`ExecutionBindingV1` is single-execution and context-specific and cannot replay
across any of those dimensions.

For `EXECUTION_STATE_ENFORCED`, the verified binding must establish that E was
actually launched or directed against T through the registered enforcement
boundary. The valid chain is:

```text
Packet P(A)
  -> ExecutionTarget T(A/P)
  -> policy-authorized registered enforcement source R
  -> VERIFIED ExecutionBinding E -> T
  -> ExecutionStateEvidence with derived effective class
  -> receipt references E/P/T/binding/evidence
```

For `EXECUTION_STATE_ATTESTED`, R must be registered with an attestation ceiling
and method and machine verification must return `VERIFIED`. Provider-specific
cryptographic attestation is not assumed. A local registered adapter observation
counts only to the exact strength declared by its registration, verifier, and
policy, with limitations disclosed.

`manual_assertion` can never derive `EXECUTION_STATE_ENFORCED` or
`EXECUTION_STATE_ATTESTED`; neither can an unregistered `provider_attested`
claim. Any evidence stronger than checkpoint-only must reference authoritative
source and binding records. For strict assured `sera_builder` origin, the builder
input A has this strong requirement; output B remains established independently
under Section 10.1. The same strong requirement applies to strict validators,
independent reviewers, and release gates. Final self-hosted 0.5.0 review and gate
permit no checkpoint-only, unregistered-observer, or manual-class exception.

Mutable changes in an unrelated checkout do not invalidate execution against
enforced T(A) while A remains governed current state. If governed state moves to
B before review recording or gate use, normal currency rules make the A evidence
historical and unusable for B. Registration B cannot upgrade, downgrade,
reinterpret, or validate evidence created under registration A; a new execution
under B requires new target-bound evidence.

canonical ExecutionReceiptV1 record according to the declared compatibility
reader; they never affect assurance. Requested target fields must match the
bound route snapshot, actual target fields report observed execution, and SERA
derives substitution classification independently under Section 12.

### 10.5 Receipt import records

The receipt importer accepts a path as input but never derives a storage path
from receipt-controlled values. Each attempt appends `ReceiptImportRecordV1`
with import ID, received time, raw SHA-256, raw byte count, parse status, target
task, observed input and output repository states when applicable, observer
class, execution-target/evidence references, observer identifier/evidence hash,
selected source-registration and execution-binding references, and reason codes.
Raw hostile input is not copied into the ledger.

The receipt's `input_state` and `output_state` are untrusted claims. Observed
states enter `ReceiptImportRecordV1` through the SERA/controller observation
boundary outside receipt-controlled JSON. A strict counted builder receipt
requires claimed output to equal the independently observed or integrated
output state. Therefore plain JSON cannot fabricate committed output B. This
proves that the governed record is bound to an observed repository state; it
does not cryptographically prove provider authorship.

For a non-mutating stage, import independently compares pre/post checkpoints and
the receipt's source/target/binding/evidence references with their authoritative
records.
Checkpoint equality and execution-window evidence remain separate results. A
receipt field such as `execution_state_attested: true`, whether top-level or
hidden in metadata, provides no stronger assurance and is rejected as an unknown
authoritative claim. Receipt import never creates or mutates
`ExecutionEvidenceSourceV1`, never treats a claimed source class as
registration, and never turns an opaque binding hash into
`ExecutionBindingV1`.

Structurally safe receipts are canonicalized and appended to
`execution-receipts.jsonl` even when they later fail task, repository, policy,
route, packet, substitution, or currency checks. Malformed or oversized input is
represented by the import record and its hash rather than unsafe raw content.

The conceptual lifecycle is:

```text
RECEIVED -> VALIDATED
RECEIVED -> REJECTED
VALIDATED + current repository movement -> STALE for current assurance
```

Receipt validity and receipt currency are separate. A validator, reviewer, or
gate receipt validly describing execution against A remains historical evidence
after movement to B, but is stale and cannot advance assurance for B. A builder
receipt may validly describe input A and output B; it is current only while the
implementation state remains exactly B.

### 10.6 Hostile-input limits

Before JSON parsing, receipt input is limited to 1 MiB. After parsing:

- the top level must be an object;
- unknown top-level fields are rejected;
- required strings are non-empty and at most 4,096 characters;
- provider, model, stage, status, hashes, IDs, and timestamps have tighter
  field-specific limits;
- hashes are lowercase 64-character hexadecimal SHA-256 values;
- timestamps are timezone-aware ISO 8601 values;
- metadata is at most 32 keys, depth 4, 64 KiB canonical JSON, with scalar or
  bounded list/object values;
- path-like metadata keys and control characters are rejected;
- non-finite numbers are rejected;
- execution IDs are data, never filenames or commands.

Receipt import performs no shell interpolation and invokes no provider command.

External execution-evidence payloads use the same 1 MiB pre-parse byte limit and
strict JSON discipline. They additionally have maximum depth 8, maximum 128
aggregate object keys, bounded 4,096-character strings with tighter ID/hash/
timestamp limits, rejected unknown fields, finite numbers only, and the same
path-containment and no-follow rules for any separately supplied artifact file.
Payload values never become paths, verifier names, module imports, commands, or
shell fragments. SERA does not interpret executable content. Raw provider
payloads, credentials, secret configuration, and unbounded diagnostics are not
persisted or reported; only content hashes, byte counts, canonical binding
results, and bounded verifier diagnostics cross the trusted boundary.

### 10.7 Execution-output binding

Successful stage evidence requires a raw output hash. Receipt import accepts an
explicit output file, reads it without following a final symlink, applies the
configured size limit, computes SHA-256, and compares it with the receipt. A
mismatch or missing required output is retained but unusable.

Verified raw output is stored only in excluded task runtime storage under a
content-addressed hash. It is absent from packets and reports. Receipt metadata
must not contain secrets or raw output. Reports expose hashes and sizes only.

## 11. Receipt validation, replay, and conflicts

Validation is ordered and machine-readable:

1. schema and bounded type validation;
2. duplicate/conflict validation;
3. task, logical repository, and Packet v4 Core Binding input-state binding;
4. canonical stage and implementation-origin policy;
5. nested input/output state schema, contract/task fingerprints, policy, and
   route binding;
6. packet hash and output hash binding;
7. requested/actual provider-model and independently derived substitution
   classification using route, policy, and trusted decision evidence;
8. identity-evidence strength;
9. execution outcome and stage-specific state fields;
10. authoritative execution-target identity;
11. source registration existence, hash/ID consistency, uniqueness, scope,
    implementation/verifier version, stage support, and target-kind support;
12. registered capability ceiling and verification-method authorization;
13. canonical `ExecutionBindingV1` identity, context agreement, and
    `binding_result: VERIFIED` for any strong class;
14. claimed versus effective evidence-class derivation under bound policy;
15. independence and sequencing prerequisites;
16. observer evidence and claimed/observed state agreement; and
17. stage-aware currency against builder output or non-mutating input state.

For `implementation_builder`, validation requires input state A, output state B,
the applicable committed-versus-working-tree policy, complete task-change
coverage, and claimed B equal to independently observed B. When strict policy
accepts `implementation_origin: sera_builder`, input A additionally requires a
policy-authorized registered source and verified binding that derives an
effective enforced or accepted attested class. Currency compares the current
implementation with B, never A. For every non-mutating role,
`output_state` is forbidden and the observed post-stage state MUST equal
`input_state`; movement produces `NON_MUTATING_STAGE_REPOSITORY_CHANGED` and the
receipt is unusable even if its verdict says success. Equal pre/post checkpoints
do not establish the execution window. Strict eligibility additionally requires
policy-accepted enforced or attested evidence whose source registration, verified
binding, target, and expected state equal `input_state` and the receipt context.

Replay behavior:

- same execution ID and same receipt hash: the repeated import is rejected as a
  duplicate; the original receipt remains eligible;
- same execution ID and different receipt hash: all receipts using that ID are
  conflicting and unusable;
- receipt from another task, logical repository, policy, route, or packet:
  rejected for binding mismatch;
- source-registration identity is reusable only when its immutable scope and
  policy permit; current configuration cannot change that historical decision;
- execution binding, target, or execution-state evidence from another execution ID, task,
  repository, contract/dynamic fingerprint, packet, stage, policy, or route:
  rejected with a precise target/evidence mismatch and never reusable;
- valid non-mutating receipt for the correct historical packet after later
  HEAD/tree movement: valid but stale, not fraudulent;
- builder receipt replayed against a task or repository whose current state is
  not its exact validated output: stale and unusable;
- a gate receipt produced while independent review was stale is retained but
  unusable for current gate assurance.

## 12. Provider/model substitution

Classifications are exactly:

```text

MANUAL_SUBSTITUTION
UNAPPROVED_SUBSTITUTION
```

An execution receipt may describe requested and actual targets, but it MUST NOT
authorize its own manual substitution. SERA derives classification from the
receipt-bound route snapshot, policy snapshot, trusted substitution-decision
ledger, and actual receipt target. Receipt import is never substitution
authorization.

### 12.1 SubstitutionDecisionV1


```text

```

No other field is excluded. `decision_id` and `authorized_execution_id` are
lowercase UUIDv4 values generated by SERA under the task mutation lock. They are
identifiers, not authentication proof. Actor identity remains only as strong as
the configured local authentication or observation boundary and is reported
truthfully.

### 12.2 Trusted creation boundary

The trusted domain operation exposed conceptually as:

```text
sera substitution authorize \
  --task <task-id> \
  --stage <canonical-stage> \
  --provider <authorized-provider> \
  --model <authorized-model> \
  --actor <actor> \
  --reason <reason>
```

resolves the active task and contract, loads the active immutable policy and
bound route snapshots, requires policy to permit manual substitution, takes the
requested target from the route rather than receipt input, captures the
authorized actual target, generates the single intended execution ID, derives
the policy result, and binds task/repository/fingerprint/stage/policy/route.
After re-reading every binding under the task mutation lock, it appends exactly
one decision and returns the `authorized_execution_id` and `decision_hash` for
the external execution. A movement or policy failure prevents append.

The command accepts local operator inputs but does not import a prebuilt
decision record and does not read authorization facts from receipt JSON. Raw
receipt data cannot invoke this operation or create stronger policy evidence.
The decision MUST be appended before external execution. Receipt validation
requires the decision ledger record to precede receipt import and requires
`decided_at` not to be later than the receipt's reported `started_at`; the
timestamp comparison is corroborating local evidence, not provider attestation.

### 12.3 Classification and single-use validation

When requested and actual targets are equal, no substitution exists. When they
differ:

- SERA derives `APPROVED_FALLBACK` when the actual target is in the ordered
  approved fallback list of the bound route. No manual decision is needed, and
  a receipt classification claim cannot change the result.
- SERA derives `MANUAL_SUBSTITUTION` only when the receipt references a valid
  `substitution_decision_hash` whose task, repository, task fingerprint, stage,
  policy, route, requested target, authorized actual target, and
  `authorized_execution_id` exactly match the receipt and current historical
  bindings.
- SERA derives `UNAPPROVED_SUBSTITUTION` for every other target difference and
  fails closed in strict assured mode.

`substitution_decision_hash` MUST be absent when targets are equal or the actual
target is an approved fallback. A redundant decision reference makes the
receipt invalid rather than allowing receipt input to force manual
classification.

For a non-fallback difference, absent trusted evidence reports
`SUBSTITUTION_DECISION_MISSING` and `MANUAL_SUBSTITUTION_NOT_AUTHORIZED`;
malformed/hash-invalid evidence reports `SUBSTITUTION_DECISION_INVALID`;
changed policy/route reports `SUBSTITUTION_DECISION_STALE`; binding or target
disagreement reports `SUBSTITUTION_DECISION_MISMATCH`; all remain
`UNAPPROVED_SUBSTITUTION` with the existing
`UNAPPROVED_PROVIDER_SUBSTITUTION` reason for strict readiness.

Each decision authorizes exactly one intended execution. The SERA-generated
`authorized_execution_id` is fixed before dispatch and MUST be used by the
receipt. The first canonical receipt for that ID represents the authorized
attempt whether it succeeds, fails, is stale, or is later found unusable; the
decision cannot authorize another ID or retry. Existing execution-ID duplicate
and conflict rules make reuse deterministic: an exact repeated import is
rejected as a duplicate, and different content for the same ID poisons that ID.
A second distinct execution referencing the decision produces
`SUBSTITUTION_DECISION_ALREADY_USED`.

An exact duplicate decision record remains observable, changes the ledger
fingerprint, produces `SUBSTITUTION_DECISION_DUPLICATE`, and blocks strict use
until explained through immutable policy. The same `decision_id` with different
content produces `SUBSTITUTION_DECISION_CONFLICT` and fails closed. A decision
for a different task, repository, route, policy, stage, requested target, or
authorized target is unusable. Policy or route movement makes the historical
decision stale for the new state; it is never rewritten.

The intended flow is:

```text
route requests A
  -> trusted `sera substitution authorize` records one decision for B and ID E
  -> external execution uses B and E
  -> receipt reports B, E, and the decision hash
  -> SERA validates route, policy, decision, and receipt independently
  -> MANUAL_SUBSTITUTION may count
```

Historical 0.4.x substitution statements remain `LEGACY_PROVENANCE`; SERA MUST
NOT manufacture modern decisions from text such as “Gemini substituted for
GPT.” A scoped self-hosting bootstrap policy may disclose and permit specified
legacy evidence, but cannot fabricate `SubstitutionDecisionV1`. Historical
provider identity is never rewritten after substitution.

## 13. Structural independence

SERA tests only observable dimensions. A counted independent review must have:

- canonical stage `independent_reviewer`;
- a receipt hash distinct from implementation and validator receipts;
- an execution ID not used by another stage;
- a separate review record bound to that receipt;
- all policy-required actor/controller, provider, model, or adapter differences;
- a current task, repository, packet, policy, route, output, and verdict binding;
  and
- the policy-required effective execution-state evidence class derived from an
  accepted source registration and verified binding to the exact target used
  for the review.

Policy may require cross-provider, cross-model, distinct source registration,
distinct observer, or distinct actor metadata, including a reviewer execution
source different from the builder execution source. This is optional rather
than universal. Review provider A and observer R are not proven independent
merely because their labels differ; policy and observable registered metadata
must establish the required separation. Missing required dimensions block
assurance. Without such
evidence SERA may prove only that a distinct receipt and stage were recorded; it
cannot prove absence of collusion or that a human/model unquestionably performed
the review. Likewise, equal controller checkpoints prove neither continuous
immutability nor that the reviewer consumed only the checkpointed checkout.

The release gate likewise requires a distinct execution ID and receipt. It may
share a provider or model only when the bound policy allows it.

## 16. Structural packet model and packet provenance v4

Packet v4 is introduced in Increment 1 because a modern receipt cannot be
receipt-backed without an immutable input packet that binds the execution
state. `PacketModelV1` therefore has an explicit feature level:

```text
schema_version: 1
feature_level: core_binding | evidence_integrity
provenance: PacketProvenanceV4
sections
```

The same versioned model evolves by satisfying a declared feature level, not by
silently changing an unversioned Markdown format. Increment 1 implements
`core_binding`; Increment 2 completes `evidence_integrity`.

### 16.1 Packet v4 Core Binding — Increment 1

`PacketProvenanceV4` at `core_binding` binds:

```text
task ID, task-contract fingerprint, and dynamic task fingerprint
input_state: ExecutionRepositoryStateV1
policy hash
route hash
canonical stage
canonical packet-model hash
rendered Markdown hash
review change fingerprint and coverage, when applicable
feature_level: core_binding
```

Both the structural JSON and rendered Markdown are validated before external
execution. The receipt's `input_packet_hash` is the canonical packet-model hash,
and its `input_state` MUST exactly match the packet input state. Increment 1 may
use minimally typed sections needed to render the existing controller context;
it MUST NOT claim the claim/evidence separation, lint, deterministic reduction,
overflow, or knowledge guarantees reserved for `evidence_integrity`.

Execution-target creation is deliberately post-packet and non-circular:

```text
Packet v4 Core binds state A and produces packet hash P
  -> policy selects exact registered source R
  -> trusted boundary creates/records target T from A, bound to P/R
  -> SERA authorizes execution ID E for stage S against T
  -> R launches/observes the external stage against T
  -> R's trusted verifier creates canonical binding E/S/P/T/R
  -> derived execution-state evidence binds the VERIFIED result
  -> receipt references E/P/T/binding/evidence
```

The packet hash does not include the later target hash, and the target hash may
include the already-final packet hash. A target is authorization/evidence, not a
packet rewrite. The binding hash includes the already-final target and packet
hashes, and evidence includes the already-final binding hash. No record hashes a
later dependent record. Minimum registry, runner, target, binding, evidence, and
validation support needed for strict modern Increment 1 review/gate is part of
Increment 1.

### 16.2 Evidence-integrity sections — Increment 2

`PacketModelV1` is a JSON model rendered to Markdown. Section kinds are:

```text
OBJECTIVE
INVARIANT
CLAIM
MACHINE_EVIDENCE
CHANGED_FILES
OWNED_FILES
TEST_RESULT
PREVIOUS_FINDING
QUESTION
```

Each section records kind, stable section ID, source/attribution, priority,
content or structured items, and estimated tokens. Markdown headings are a
presentation of this model, not the type system.

At this point the model declares `feature_level: evidence_integrity` and retains
all Core Binding fields. It also binds the knowledge fingerprint and context
manifest hash. A reader rejects a packet whose declared feature level omits any
field or invariant required by that level.

### 16.3 Packet lint — Increment 2

Lint emits versioned structured findings without rewriting source content.
Unsupported controller assertions such as “verified implementation”, “fully
compliant”, “secure”, “production-ready”, or “all tests prove correctness” are
flagged when present in controller-authored claims. Attributed machine evidence,
quoted task text, and prior findings are preserved and labeled.

Blocking lint prevents packet dispatch according to policy. Findings persist in
`packet-lint.jsonl` and bind to packet hash.

## 17. Deterministic context reduction

Context selection is deterministic for the same repository, task, policy,
packet stage, and budget. Ranking order is:

1. mandatory semantic section class;
2. stage priority;
3. explicit inclusion;
4. changed-file status;
5. owned-file status;
6. dependency distance;
7. relevance score descending;
8. estimated tokens ascending;
9. normalized path or stable section ID lexicographically.

Mandatory retained semantic classes are task objective, safety/security
invariants, acceptance criteria, and relevant unresolved findings. They are
retained before optional source context.

When estimated context exceeds budget, SERA emits a reduced packet and a
versioned overflow manifest listing configured budget, original estimate,
selected items, excluded items, token estimates, and deterministic reasons.
Changed-file review evidence retains existing complete-coverage guarantees. If
minimum evidence for every changed file or one mandatory semantic item cannot
fit, generation fails with a specific reason rather than truncating silently.

## 19. TOCTOU checkpoints

Controller repository, active-contract, policy, source-registration, and target
identity are checked at eleven mandatory boundaries:

1. **Task-contract adoption:** capture the old active contract,
   repository/HEAD/tree, and policy; construct the embedded new contract; then
   re-read all bindings before appending one adoption record. Movement fails
   without changing the active contract.
2. **Packet preparation:** capture the complete input
   `ExecutionRepositoryStateV1` and active task identity before reading task
   context and after writing packet artifacts. Movement aborts dispatchable
   packet creation; Packet v4 never binds a state assembled across two moments.
3. **Substitution authorization:** capture active task/repository/policy/route,
   derive requested target from the route, construct the single-use decision,
   and re-read every binding before append. Movement prevents authorization.
4. **Source selection:** resolve the exact policy-accepted registration hash,
   validate its unique source ID, scope, ceiling, stage/target support, and
   verification method, then re-read the record before target authorization.
   Registry drift or current-config substitution cannot change the selection.
5. **Execution-target creation:** after Packet v4 hash P and any required
   execution-specific substitution authorization are final, capture complete
   input state A, stage, execution ID, policy, and route; create target T from A;
   independently record target identity/creation evidence; then re-read P/A,
   selected source R, and every authorization binding before appending
   `ExecutionTargetV1`.
6. **Runner launch and binding verification:** bind E/R/T/P before launch; after
   completion revalidate target and context, invoke only R's registered verifier,
   and append canonical `ExecutionBindingV1` with its actual result. Movement or
   verifier mismatch produces failed/indeterminate history, never strong evidence.
7. **Receipt import:** compare receipt input with the immutable Packet v4 Core
   Binding and trusted substitution decision; independently observe repository
   checkpoints before authorization/execution and after execution. For a builder,
   compare claimed output with the exact integrated/observed output. For a
   non-mutating role, require both checkpoints to equal input state. Validate the
   separate source/target/binding/evidence chain. Append the observation to the
   import record; movement prevents current classification but never rewrites
   the receipt.
8. **Receipt validation:** validate intrinsic fields and historical bindings
   independently from stage-aware currency. Builder currency is current output
   B; non-mutating currency is current input A, while execution-window
   eligibility comes from registered source plus verified binding evidence rather
   than endpoint equality.
9. **Review recording:** verify receipt, selected source, target, binding,
   evidence, prerequisites, packet, and current identity before and after
   appending the review record.
10. **Gate recording:** perform the review checks plus require a current accepted
   independent review at both checks.
11. **Seal generation:** under the task mutation lock, derive state, selected
   source registrations/bindings, all bound
   non-seal evidence fingerprints, and the pre-append seal-ledger fingerprint;
   construct the candidate; then re-read every bound value immediately before
   appending exactly one record to `seals.jsonl`. Any movement fails before the
   append. Only after the authoritative append completes may SERA atomically
   replace the optional derived `seal.json` pointer. Pointer failure never
   rewrites or removes the appended record.

Mandatory scenario:

```text
HEAD A -> packet A -> external execution -> HEAD B -> receipt A
```

Result: receipt A is retained and may be intrinsically valid for packet A, but
is stale relative to B and cannot advance current assurance.

Controller checkpoints and the external execution window are different TOCTOU
domains. In `checkpoint A -> external execution observes transient B -> restore
A -> checkpoint A`, SERA records checkpoint equality but MUST derive
`EXECUTION_WINDOW_NOT_ESTABLISHED` under strict exact-state policy unless valid
enforced or attested execution-state evidence independently binds execution to
A. Checkpoint polling frequency does not become a continuous-immutability claim.

Builder-specific scenarios are also mandatory:

```text
packet/input A -> builder claims B -> importer observes B -> current B: eligible
strict sera_builder input A without accepted R + VERIFIED E -> T(A): blocked
strict sera_builder input A with accepted R + VERIFIED E -> T(A), observed B: eligible
packet/input A -> builder claims B -> importer observes C: output mismatch
packet/input A -> builder claims working tree A+delta under strict policy: blocked
packet/input A -> reviewer or gate moves repository to B: stage invalid
packet/input A -> isolated builder emits patch only: no strict modern builder provenance
```

## 20. Seal v3

### 20.1 Authority, identity, and bindings

`seals.jsonl` is the authoritative persisted Seal v3 history. Seal v3 records
are append-only historical evidence. SERA MUST NOT update, replace, delete, or
rewrite a previously persisted Seal v3 record during ordinary operation. Every
successful modern sealing operation appends exactly one record. A later seal
does not supersede history by removal; it adds another historical observation.

Each Seal v3 record contains:

```text
schema_version: 3
seal_id
SERA version
task ID, task-contract fingerprint, and dynamic task fingerprint
active task-contract schema, contract hash, and adoption hash when applicable
logical repository identity
sealed HEAD and tree
implementation origin
selected builder input state, output state, receipt/import hashes, and
observed-output agreement
selected per-stage source ID, exact source-registration hash, source type,
capability ceiling, verification method/version, and policy decision
selected per-stage execution-target, ExecutionBindingV1, and execution-state
evidence hashes; binding result; claimed/effective evidence classes; and
exact-state eligibility
per-stage provenance classes and overall provenance
active policy hash
knowledge fingerprint
ordered evidence-ledger fingerprints
AssuranceState fingerprint
required and satisfied stages
sealed_at
prior_seal_ledger_fingerprint
seal_record_hash
```

Evidence collection fingerprints cover task-contract history, policy snapshots,
route snapshots, substitution decisions when substitution influenced readiness,
execution targets, task-scoped execution bindings, execution-state evidence,
receipt imports, execution
receipts, verification, reviews, packet lint, and any other collection that
influenced readiness. The seal therefore binds which validated task contract,
exact source registrations, target/binding/evidence records, effective class,
verifier result, and policy classification were used by assurance; it
does not strengthen those records or turn checkpoint equality into execution-
window proof. It also binds which trusted decision authorized a counted manual
substitution and which builder output state became the implementation state
considered by assurance. Filenames are diagnostics, not identity. Appending
a duplicate or failed record after sealing changes the relevant ledger
fingerprint and makes the seal stale, even when current stage selection remains
successful.

The repository-global source-registry ledger fingerprint is deliberately absent
from task readiness and Seal v3. Each seal embeds the exact canonical selected
registration hashes/records that influenced assurance. Appending an unrelated
source registration therefore does not stale a task, while mutation, deletion,
hash mismatch, conflict, or policy movement affecting a selected registration
fails validation. This does not create a circular relationship: registrations
hash only themselves; bindings hash registrations and targets; state evidence
hashes the binding reference; receipts/reviews select those records; the seal
binds their already-computed hashes and task-scoped ledger fingerprints.

`prior_seal_ledger_fingerprint` is the canonical ledger fingerprint of the
complete authoritative `seals.jsonl` prefix as it existed before this record
was appended; a missing ledger uses the schema-defined empty-ledger
fingerprint. The field binds prior seal history without requiring a record to
hash a ledger that already contains itself. The ordered evidence-ledger map in
the record binds only assurance-relevant non-seal collections that existed
before append.

`seal_id` is a lowercase UUIDv4 generated once while the task mutation lock is
held and is unique within a task's seal ledger. It identifies one logical seal;
it is not an authentication claim. Reuse of a `seal_id` with different content
is a conflict. The stable record identity is computed exactly as:

```text
seal_record_hash = SHA256(canonical SealV3 record excluding seal_record_hash)
```

No other field is excluded. The hash uses the canonical JSON rules in Section
5 and lowercase hexadecimal encoding.

### 20.2 Seal-ledger validation and current selection

`seals.jsonl` follows Section 5. Append order is authoritative. Readers MUST
parse the complete ledger and validate every record, including its schema,
record hash, task/repository binding, unique identity, and
`prior_seal_ledger_fingerprint` against the actual prefix. Malformed or
truncated lines block assurance, including an incomplete final line. Record
reordering, deletion, mutation, or insertion changes the ledger fingerprint;
normalization MUST NOT make any record disappear. Platform newline style and
insignificant JSON whitespace are non-semantic after normalization.

An exact duplicate record remains present and observable, changes the ledger
fingerprint, produces `SEAL_RECORD_DUPLICATE`, and blocks strict assured seal
acceptance until the duplicate is explained through an explicit immutable
policy decision. The duplicate is never deleted during ordinary operation. The
same `seal_id` with different content produces `SEAL_RECORD_CONFLICT` and
`SEAL_HISTORY_CONFLICT` and fails closed.

Seal validity and seal currency are separate. Historical validity asks whether
the record was structurally valid, internally consistent, properly bound to
the ledger prefix, and eligible for the state it sealed. Currency compares
those preserved bindings with the current task, repository, HEAD/tree, policy,
knowledge, and non-seal evidence state. A historically valid seal can therefore
be `STALE` without being fraudulent.

Current-seal selection MUST:

1. parse the complete seal ledger;
2. validate all records and prefix relationships;
3. derive each record's historical validity;
4. compare each valid candidate with current task, repository, and evidence
   state;
5. select the newest eligible `CURRENT` record according to ledger order; and
6. fail `sera check --require-seal` closed with an explicit reason when no
   current record exists.

Historical stale, failed, and non-current records remain inspectable. The last
physical line is not trusted merely because it is last.
An absent `seals.jsonl` produces `SEAL_HISTORY_MISSING`; an empty ledger has no
current seal and likewise cannot satisfy `--require-seal`.

For the sequence `HEAD A -> verification A -> review A -> gate A -> seal A`,
followed by implementation change and the complete assurance sequence for
`HEAD B -> seal B`, the authoritative ledger contains record 1 for A and record
2 for B. Both remain inspectable; A is historically valid but `STALE` for B,
and B is `CURRENT`. No replacement occurs. Likewise, appending a verification
attempt after seal A changes the bound verification-ledger fingerprint and
makes A stale even if HEAD/tree did not move. A new seal requires the full
current policy-defined assurance process; SERA MUST NOT mutate A.

### 20.3 Sealing algorithm and current pointer

`sera seal` performs the following conceptual algorithm:

1. acquire the task mutation lock;
2. derive the single authoritative `AssuranceState` and require seal
   eligibility;
3. capture active task-contract identity and history, task/repository identity,
   HEAD/tree, policy, knowledge, exact selected source registrations, every bound
   non-seal evidence-ledger fingerprint, and the prior seal-ledger fingerprint;
4. construct canonical Seal v3, generate its `seal_id`, and compute
   `seal_record_hash`;
5. re-read active task contract, repository identity, HEAD/tree, policy-selected
   source records, every bound evidence fingerprint, and the complete prior
   seal-ledger state;
6. if any captured value changed, fail with `SEAL_HISTORY_CHANGED` or the more
   specific evidence reason without appending;
7. append exactly one canonical Seal v3 line to `seals.jsonl` and complete the
   append using the repository's supported persistence primitive;
8. only after successful append, optionally atomically update the derived
   `seal.json` current pointer; and
9. release the lock.

Append occurs under the task lock. SERA reports append success only after the
platform write operation completes, but makes no durability claim beyond the
guarantees of the operating system and filesystem abstraction it actually
uses. A crash or partial append that leaves malformed/truncated JSONL blocks
modern assurance; readers MUST NOT ignore the final record.

The optional 0.5.0 `seal.json` pointer contains enough identity (at minimum
schema version, `seal_id`, `seal_record_hash`, and post-append seal-ledger
fingerprint) to compare it with the authoritatively derived current record. It
is optional, derived, non-authoritative, replaceable, and reconstructable.
Deleting it does not delete seal history. Changing it does not change
authoritative history. A missing pointer may be regenerated. An inconsistent
pointer produces `SEAL_POINTER_MISMATCH` and MUST fail validation or be
regenerated; it never overrides the ledger.

If authoritative append succeeds but pointer update fails, the Seal v3 record
remains successfully recorded and all earlier records remain unchanged. The
command reports a recoverable pointer-update error such as “seal recorded
successfully; current pointer update failed.” It MUST NOT roll back, replace,
or erase the authoritative append.

`sera check --require-seal` reads and validates `seals.jsonl`, derives the
current seal from the complete history and current `AssuranceState`, and fails
closed if none is current. It never trusts `seal.json` independently. When a
pointer exists it is validated against the authoritative selection; mismatch
produces `SEAL_POINTER_MISMATCH` and fails validation until the pointer is
regenerated or removed, without changing ledger truth.

Seal v2 remains readable but is `LEGACY_PROVENANCE` for receipt-backed assured
acceptance. It remains a historical `seal.json`, is not converted to v3, and is
not inserted into `seals.jsonl` as though it had been created there. Seal v3
creation requires one current `AssuranceState` and repeats the state/identity
checks immediately before authoritative append.

An Increment 1 bootstrap Seal v3, when the immutable policy permits it, MUST
record legacy/unversioned verification, modern receipt-backed review/gate
evidence, and `overall_provenance: mixed`. It is an increment checkpoint only
and cannot be selected as the final strict 0.5.0 release seal. The final Seal v3
requires current Verification v2, policy-accepted source registrations, verified
bindings, and effective enforced or attested evidence for every strict
origin-required builder/validator input and for final review/gate, plus modern
provenance for every required release stage.

## 22. Compatibility and migration

Compatibility is read-time and conservative:

- task v1: readable as legacy/pre-existing; no invented policy, knowledge, or
  builder receipt, and no automatic Task v2 contract;
- historical manual provider/substitution text: readable only as an assertion
  with `LEGACY_PROVENANCE`; no `SubstitutionDecisionV1` is manufactured;
- unversioned verification: readable, retains command/result/hash, lacks modern
  environment and repository provenance, and may count only as the explicitly
  scoped Increment 1 self-hosting bootstrap exception described below;
- unversioned review: readable as manual `LEGACY_PROVENANCE`;
- receipt/review evidence without authoritative `ExecutionEvidenceSourceV1`,
  `ExecutionTargetV1`, `ExecutionBindingV1`, and `ExecutionStateEvidenceV1`:
  retained at its actual legacy or checkpoint-only strength; no source
  registration, target, binding, enforcement, or attestation record is
  manufactured;
- packet v3: readable for diagnostics but cannot satisfy a modern receipt;
  Packet v4 Core Binding must be regenerated in Increment 1;
- seal v2: readable in its historical `seal.json` location as
  `LEGACY_PROVENANCE`, but cannot satisfy modern strict receipt-backed
  assurance and is never silently converted or copied into `seals.jsonl`.

Default legacy policy may preserve non-assured historical workflows. Assured
tasks reject legacy provenance unless an explicit immutable override snapshot
records actor, reason, scope, stage, increment, and policy decision. For this
self-hosted upgrade, only legacy verification may be enumerated for the
Increment 1 checkpoint. Legacy review/gate evidence, missing builder state,
missing Packet v4 Core Binding, insufficient execution-window evidence, and
unregistered sources, missing/failed bindings, and unbound substitutions remain
blocking. No task is silently upgraded, and final
strict release ignores the bootstrap exception.

The 0.5.0 self-hosting task began under task schema v1. A policy override alone
cannot promote it. After Increment 1 provides the provenance foundation, the
task MUST cross an explicit `TaskContractAdoptionV1` boundary before modern
packets, receipts, reviews, gates, or Seal v3 can bind a Task v2 fingerprint.

When `seals.jsonl` does not exist, modern history is empty and begins only when
the first real Seal v3 record is created. Migration MUST NOT manufacture a v3
record from a v2 file. A legacy v2 `seal.json` and an optional modern derived
pointer use the same historical pathname but are distinguished by strict schema
readers and task migration state. When that pathname contains a legacy v2 seal,
modern sealing MUST leave it unchanged and omit the optional pointer rather than
replace historical evidence. Current Seal v3 is still derived from
`seals.jsonl`; creating the first v3 history does not rewrite the legacy
artifact merely to simulate prior history.

### 22.1 Self-hosting Task v1 adoption sequence

The executable self-hosting transition is:

1. the original Task v1 and all pre-adoption evidence remain historical under
   SERA 0.4.2;
2. Increment 1 implements the provenance foundation: task-contract adoption,
   receipts/import observation, trusted substitution decisions, builder
   pre/post execution state, Packet v4 Core Binding, repository source registry,
   `ExecutionEvidenceSourceV1`, `ExecutionBindingV1`, binding verification,
   source-policy authorization, the registered external runner, target/evidence
   support, and modern review/gate receipt support; no native provider dispatch
   is introduced;
3. the administrative operation creates or resolves the exact registered
   external-runner source R, and the candidate policy accepts R's registration
   hash with enforced capability for the self-hosting review target/stage;
4. the operator explicitly adopts Task v2 with actor, reason, `pre_existing`
   origin, empty/unassessed knowledge, and narrow structured bootstrap
   limitations; original Task v1 remains unchanged and inspectable;
5. SERA regenerates a `feature_level: core_binding` Packet v4 for the exact
   current Increment 1 state and active Task v2 fingerprint;
6. current legacy verification runs and is recorded as
   `LEGACY_PROVENANCE`/bootstrap-permitted only when the immutable policy allows
   that exact Increment 1 verification scope;
7. SERA creates execution E and exact target T(A/P), R launches/directs the
   provider-neutral external reviewer against T, R's registered verifier creates
   a canonical `ExecutionBindingV1` with `VERIFIED`, and only then is effective
   `EXECUTION_STATE_ENFORCED` evidence eligible;
8. the external reviewer output/receipt references E/P/T/binding/evidence and is
   imported normally; receipt/review validation rechecks R, policy, binding, and
   all execution context before the modern review can count;
9. `AssuranceState`, reports, and any checkpoint Seal v3 record selected source,
   binding, target/evidence strength, modern review, legacy verification, and
   `overall_provenance: mixed` without strengthening history;
10. the Increment 1 exit gate passes only under that explicit bootstrap policy,
   with every modern capability introduced in Increment 1 required and no
   unresolved blocking finding;
11. Increment 2 implements Verification v2, full Packet v4 evidence integrity,
   knowledge fingerprints, claim/evidence separation, lint/context/overflow,
   and the remaining evidence-integrity TOCTOU controls;
12. knowledge discovery that changes contract identity triggers a second
    explicit Task v2 adoption; the Increment 1 contract and review remain
    historical;
13. packets and verification are regenerated as fresh Packet v4
    `evidence_integrity` and Verification v2 evidence for the new contract;
14. a fresh source-authorized, verified-binding, target-bound exact-state
    Increment 2 independent review replaces no history and is current only for
    that Increment 2 state;
15. Increment 3 adds explain/report, legacy migration presentation,
    documentation, justified CI, and release behavior;
16. a fresh final exact-state independent review uses a policy-accepted source,
    verified binding, and effective enforced or attested evidence and does not
    reuse either earlier increment review;
17. a distinct fresh release gate uses an independently validated source/
    binding/evidence chain and evaluates the already-current final review;
18. any strict `sera_builder` origin claim has strong input execution evidence
    against A plus independently observed committed output B; origin-required
    validator evidence meets the same source/binding rules;
19. SERA appends Seal v3 for the exact final release HEAD/tree, active Task v2,
    assessed knowledge, complete Packet v4, Verification v2, current
    origin-required builder/validator evidence, selected registrations, verified
    bindings, review, and gate; and
20. `sera check --require-seal` succeeds with entirely modern required-stage
    provenance and no legacy-verification exception.

`bootstrap_limitations` records actor, reason, exact Increment 1 scope, legacy
verification evidence allowed, modern stages still required, policy result,
adopted contract, and assurance limitations. It does not mean any old evidence
becomes modern. The final report exposes the adoption point, legacy boundary,
origin, mixed provenance, and all limitations.

### 22.2 Migration risks and controls

| Risk | Required behavior |
| --- | --- |
| Config v1 has lanes but no stage policy snapshot | Translate in memory, label the source schema, and require explicit adoption before a strict assured task can gain modern policy semantics. Do not rewrite config during a read. |
| Task v1 lacks origin, repository identity, policy, and knowledge | Normalize in memory as legacy/pre-existing with absent modern bindings; never infer or persist them from current state. Strict assurance requires explicit `TaskContractAdoptionV1`; preserve v1 `task.json`, append the embedded v2 contract to `task-contracts.jsonl`, and use a different modern fingerprint. |
| Historical substitution text has no trusted decision source | Preserve it as `LEGACY_PROVENANCE`; never manufacture a `SubstitutionDecisionV1` or let the assertion authorize a modern receipt. |
| Existing assured reviews were accepted from typed reviewer names | Preserve and display them as legacy, but never use them for Increment 1's required modern exact-state review or final strict release. |
| Equal pre/post checkpoints exist without execution-window evidence | Preserve them as `CHECKPOINT_OBSERVED`; report the limitation and never synthesize an enforced/attested target or strict exact-state eligibility. |
| Historical evidence names a registered source or opaque binding hash but has no authoritative registration/binding | Preserve the claims as manual/legacy diagnostics; never manufacture `ExecutionEvidenceSourceV1` or `ExecutionBindingV1`, and never derive a strong effective class. |
| Source registration A is followed by registration B or verifier-version change | Preserve A and evaluate historical evidence with A and its governing policy; B has a new source ID/hash, changes no historical classification, and requires a new execution/binding/evidence chain. |
| Current source configuration removes A | Continue using the task-bound policy snapshot for historical evaluation; use explicit policy and task-contract adoption for a current transition, with no deletion-based retroactive revocation. |
| New policy excludes A | Evidence under the old policy remains historical, but cannot satisfy the new contract/policy; require new evidence under an accepted source. |
| Legacy verification is needed to bootstrap Increment 1 | Permit only through an immutable, stage-specific Increment 1 policy exception; derive `overall_provenance: mixed`, forbid the exception from covering review/gate/builder/packet/substitution requirements, and reject it for final release. |
| Packet v3 has no policy/route/model/input-state binding | Preserve for audit and require Packet v4 Core Binding regeneration before any modern receipt-backed execution. |
| Seal v2 omits receipt and policy ledgers | Read the existing `seal.json` as `LEGACY_PROVENANCE` at its historical location; do not rewrite, convert, or copy it into `seals.jsonl`; modern history starts with the first actual Seal v3 creation, and modern assured acceptance requires a fresh v3 record. |
| Mixed legacy and v2 ledger lines | Parse each line through its declared or compatibility schema, retain order, and fingerprint the normalized sequence; malformed lines block rather than disappear. |
| New domain modules replace logic formerly in `core.py` | Characterization tests hold existing non-provenance behavior while new tests prove the domain module is authoritative. Facades delegate rather than duplicate. |
| Configuration changes during an active task | Continue using the contract-bound snapshot and surface the difference; append a candidate policy snapshot through an explicit actor/reason event, then use explicit task-contract adoption before it becomes active. |
| Increment 2 discovers knowledge for an unassessed Increment 1 contract | Preserve the original empty/unassessed contract and require another explicit task-contract adoption with the discovered knowledge; do not mutate it through read or policy adoption. |

These are intentional compatibility boundaries, not automatic upgrades.

## 23. Security model

### 23.1 Threats and controls

| Threat | Control |
| --- | --- |
| Path traversal or absolute-path escape | Normalize repository-relative paths; reject absolute paths, `..`, and resolved root escape. |
| Symlink attacks | Reject symlink escapes; no-follow final input where supported; verify resolved containment and file identity. |
| Receipt/cache poisoning | Strict bounded schemas, canonical hashes, content-addressed output storage, append-only import audit. |
| Receipt modification | Canonical receipt hash plus ledger fingerprint and downstream seal binding. |
| Output replacement | Content hash comparison on import and before counted use. |
| Builder falsely claims output B | Treat receipt output as untrusted; require import-side observation/integration evidence and exact claimed/observed `ExecutionRepositoryStateV1` equality. |
| Builder output changes after execution | Compare current implementation state with the validated builder output, surface `BUILDER_OUTPUT_STALE`, and require new evidence for the changed state. |
| Non-mutating stage changes the repository | Forbid `output_state`, observe before/after state, and fail with `NON_MUTATING_STAGE_REPOSITORY_CHANGED`. |
| Transient A -> B -> A between equal checkpoints | Classify endpoint evidence only as `CHECKPOINT_OBSERVED`; strict exact-state assurance requires enforced or accepted attested execution-window evidence. |
| Receipt fakes execution-state attestation | Treat every receipt source/target/binding/evidence field as untrusted; only policy-authorized registered sources and machine-verified canonical records created outside receipt JSON can carry strength. |
| Fake “registered” adapter or observer name | Resolve `source_id` plus exact `source_registration_hash` only from the authoritative repository registry; labels and receipt fields have no trust effect. |
| Forged source/evidence class | Preserve the claim only as bounded diagnostics and derive effective class from registration ceiling, verifier result, method strength, stage/target support, and policy. |
| Source capability escalation | Reject a claimed or verifier result above the immutable registered ceiling with `EXECUTION_EVIDENCE_SOURCE_CAPABILITY_INSUFFICIENT`. |
| Source registration replacement or same-ID conflict | Append-only registry, canonical record hashes, new IDs for every material version, and fail-closed conflict handling; never update in place. |
| Source registration/configuration drift | Evaluate history using the exact task-policy-bound registration hash; current configuration creates only a candidate selection until explicit adoption. |
| Fake or opaque execution-binding hash | Require resolution to canonical `ExecutionBindingV1`, recompute its hash, and validate all context plus `VERIFIED`; a hash-shaped string proves nothing. |
| Binding verifier spoof or external verifier selection | Select verifier implementation only from immutable registration inside the trusted domain boundary; external evidence cannot name/import code or select a method. |
| Source accepted by global config but not task policy | Treat configuration as candidate input only; the immutable active `PolicySnapshotV1` is the sole authorization authority. |
| Stale source or execution-binding replay | Registration may be reusable within scope; binding may not. Bind execution evidence to task/repository/contract/policy/route/stage/execution/target/packet and reject any mismatch. |
| Source supports validator but not reviewer | Validate `supported_stages` for the exact stage and reject reviewer use as unauthorized. |
| Source target-kind mismatch | Validate `supported_target_kinds` against authoritative target kind and reject mismatches. |
| Manual assertion upgraded to enforced/attested | Manual or unregistered records have a checkpoint/legacy ceiling regardless of claimed source class, observer ID, or evidence hash. |
| Hostile external evidence payload | Apply strict byte/depth/key/string/type/unknown-field/path limits, no shell or executable interpretation, persist only hashes and bounded verifier results, and exclude secrets/raw payloads from reports. |
| Execution-target substitution | Bind target to task/repository/contract/dynamic fingerprint/packet/stage/policy/route/execution ID and reject any receipt or authorization mismatch. |
| Execution target drifts after identity creation | Revalidate content-addressed/Git identity and evidence binding; a changed target has a different identity or produces `EXECUTION_TARGET_MISMATCH`. |
| Immutable but stale target T(A) approves current B | Separate historical validity from currency and require governed current state A at review recording and gate use; target A cannot approve B. |
| Isolated-worktree identity mismatch | Require the exact builder commit/tree/change identity to be integrated and observed in the governed repository; reject patch-only or different cherry-picked commit identity for strict provenance. |
| Packet/input-state mismatch | Bind Packet v4 Core Binding and receipt `input_state` to the same canonical state object and reject any mismatch. |
| Builder output replay across task or repository | Bind both state objects to logical repository, active task-contract fingerprint, dynamic task fingerprint, packet, policy, and route; validate current output currency. |
| Stale receipt reuse | Use stage-aware input/output state, fingerprint, policy, route, and packet bindings with separate validity and currency evaluation. |
| Task ID collision | Existing collision avoidance plus repository/task binding; execution ID conflict poisons the ID. |
| Hash confusion | SHA-256 fields have named domains and strict lowercase encoding; ledger hashing uses domain separators. |
| Untrusted JSON | Size, depth, key-count, type, unknown-field, Unicode-control, and finite-number checks. |
| Shell/provider command injection | Receipt data never becomes a command; native dispatch absent. |
| Prompt injection in repository files | Typed attribution distinguishes repository content, claim, instruction, invariant, and machine evidence. Repository text cannot change controller policy. |
| Secret leakage | Credential-bearing remotes stripped; raw output excluded; receipt metadata bounded; secret-risk packet findings block dispatch rather than silently redact evidence. |
| Controller-boundary TOCTOU | Task lock plus before/after identity checks at all SERA mutation and recording transitions. |
| External execution-window TOCTOU | Do not infer continuous state from checkpoints; require a policy-authorized source and verified immutable-target binding or accepted attestation for strict exact-state stages. |
| Concurrent duplicate imports | Locked uniqueness/conflict evaluation and atomic append. |
| Receipt self-authorizes manual substitution | Receipt classification is non-authoritative; derive it from immutable route/policy state, trusted `substitution-decisions.jsonl`, and actual target. |
| Forged or replayed substitution authorization | Create decisions only through the SERA mutation boundary, bind one SERA-generated execution ID plus task/repository/fingerprint/stage/policy/route/targets, and reject reuse. |
| Substitution after route or policy drift | Treat the historical decision as stale and unusable for the changed binding; never rewrite it. |
| Silent legacy task promotion | Compatibility readers return `TASK_CONTRACT_LEGACY`; only explicit locked contract adoption can create a modern fingerprint. |
| Task-contract rewriting or projection tampering | Make `task-contracts.jsonl` authoritative and append-only; treat modern `task.json` only as a derived projection and preserve legacy v1 in place. |
| Stale or cross-repository contract adoption | Bind previous contract, repository identity, HEAD/tree, and policy; re-read them before append and fail closed on mismatch. |
| Contract-adoption TOCTOU | Hold the task mutation lock through capture, construction, re-read, and one-record append; update any derived projection only afterward. |
| Seal pointer tampering or pointer/ledger disagreement | Treat `seal.json` as derived only; validate it against the current record selected from `seals.jsonl`, report `SEAL_POINTER_MISMATCH`, and never let it override ledger truth. |
| Seal history deletion, mutation, or reordering | Order-sensitive ledger and prefix fingerprints make changed history observable when compared; malformed relationships fail closed and no reader normalizes a record away. |
| Duplicate or conflicting seal records | Preserve exact duplicates, surface `SEAL_RECORD_DUPLICATE`, and block strict acceptance until explicitly explained; the same `seal_id` with different content is `SEAL_RECORD_CONFLICT` and fails closed. |
| Truncated or partial seal append | Append under the task lock; malformed or incomplete lines, including the final line, block modern assurance and are never silently ignored. |
| Seal replay between tasks or repositories | Bind task fingerprint and logical repository identity in each record and validate them before historical validity or current eligibility can count. |

Local SHA-256 and prefix fingerprints detect inconsistency relative to available
state; they are integrity mechanisms, not remote attestation and do not prevent
a malicious local actor from coherently rewriting the entire repository and
task history. A local registered runner or adapter can also be controlled by the
same local actor as the repository; `EXECUTION_STATE_ATTESTED` means only that the
policy-approved registered verifier established its declared property to that
source's documented strength. No new runtime dependency or universal
cryptographic attestation claim is required.

## 26. Self-hosting governance

The self-hosting task was created under SERA 0.4.2 before this specification was
tracked. Its task baseline is the verified HEAD/tree in section 2.

`.sera/tasks/20260830T034346Z-sera-0-5-0-execution-provenance/self-hosting-findings.jsonl`
is an append-only runtime record with:

```text
observation
affected SERA capability
current workaround
proposed improvement
priority
increment discovered
status
```

Findings are summarized into tracked release documentation in Increment 3.
Work performed before receipt support is labeled manual/legacy. Increment 1,
Increment 2, and final release reviews use fresh contexts and exact state. No
historical review is rewritten to appear current.

The runtime findings ledger is maintained throughout all increments. It records
the reusable mutating-stage lesson that governed input and independently
observed output identities must be separate, and the self-hosting lesson that an
increment cannot require a proof artifact whose schema or binding primitive is
deferred. Increment 1 mixed provenance and its verification limitation remain
visible until fresh Verification v2 evidence supersedes the limitation for
current assurance; history is never strengthened retroactively.

The ledger also records that equal controller pre/post repository checkpoints
cannot prove execution-window immutability. The current specification workaround
for strict independent review/gate is a versioned immutable exact-state target
with enforced execution binding or accepted registered attestation. This
means a policy-authorized immutable source registration and machine-verified
canonical binding, not a label or hash alone. This execution-state primitive
belongs in Increment 1 because its exit review consumes it; the finding remains
append-only history after specification remediation.

`SHF-014` records the reusable SR-007 lesson: a trusted evidence class requires
an independently governed trust root. Calling an adapter “registered” or storing
a hash does not make its claims authoritative; immutable verifier identity and
version, capability ceiling, policy authorization, and machine-verified
execution binding must be explicit. The remediation is additive to SHF-013:
SHF-013 distinguishes checkpoint time from the execution window, while SHF-014
establishes why the stronger source and binding evidence is trustworthy enough
to classify at all.

## 27. Documentation obligations

Release documentation covers execution receipts, roles, implementation origin,
builder input/output states and observed-output limitations,
execution target/evidence schemas, checkpoint/enforced/attested strength,
execution-evidence source registry/identity/capability and trusted registration,
execution-binding schema/verifier/result and claimed/effective class derivation,
trusted substitution decisions, task-contract adoption and bootstrap boundaries,
policy snapshots, receipt identity limits, legacy provenance, review freshness,
mixed provenance, Packet v4 feature levels, verification history, packet lint,
context reduction, knowledge fingerprints,
`sera explain`, `sera report`, seal v3, migration, and the deferred
native-dispatch adapter boundary.

It contains distinct sections “What SERA can prove” and “What SERA cannot
prove.” Provider CLI identity, external authorship, manual historical execution,
copied repository identifiers, execution-window state, and independence beyond
observed dimensions are explicit limitations.

“What SERA can prove” states that equal trusted checkpoints establish equality
only at those checkpoints; valid enforced evidence establishes operation against
the recorded immutable/content-addressed target to the strength of a
policy-approved registered source and verified canonical binding; and accepted
attested evidence establishes only what the registered verifier and capability
support. “What SERA cannot prove” states that checkpoint equality
does not exclude transient A -> B -> A, receipt text cannot establish target
enforcement or attestation, and SERA does not infer provider authorship,
continuous monitoring, non-collusion, or execution against A beyond available
trusted evidence.

## 28. Resolved and deferred decisions

All implementation-blocking design decisions are resolved by this specification.

Deliberately deferred beyond 0.5.0:

- native provider invocation and provider-specific adapters;
- cryptographic receipt signing or provider attestation protocols;
- universal remote attestation, code-signing requirements, or proof that a local
  registered source is independent from the local repository actor;
- remote transparency logs or database storage;
- automatic policy adoption for active tasks;
- proof of human/model non-collusion beyond observable receipt dimensions.

These deferrals do not weaken the 0.5.0 invariant: absence of evidence remains a
blocked or explicitly limited state, never inferred assurance.
